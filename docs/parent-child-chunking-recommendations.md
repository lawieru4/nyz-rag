# 父子块切片改造建议

日期：2026-10-23

状态：按本文第二、三节完成了实验 A、B、C（2026-10-24），结果见[评估方案](evaluation-plan.md)第 8.6 节：没有正收益，暂不上线。本文补充现有[切片方案](chunking-design.md)和[评估方案](evaluation-plan.md)，不替代它们。

## 一、总体原则

按「先基线，再拆分验证，最后决定是否上线」推进。

父子块的核心假设是：小块负责定位，父块负责补足回答证据。但「小块检索、大块回答」不一定提升效果：扩展可能补全证据，也可能挤掉其他相关文章、引入无关内容。因此，应先建立可复现基线，再通过对照实验决定是否采用。

## 二、拆成三个实验

不要一次同时修改子块长度、父块扩展、聚合打分、`topK` 和上下文预算。

| 实验 | 检索单元 | 回答上下文 | 验证问题 |
| --- | --- | --- | --- |
| A：现有基线 | 当前约 800 字切片 | 原切片 | 当前效果 |
| B：只改小块 | 新子块，约 200～500 字 | 命中子块，不扩展 | 小块是否提高定位能力 |
| C：父子块 | 与 B 完全相同 | 命中后扩展父块、去重 | 补充上下文是否真正有益 |

B 与 C 共用同一份索引、同一批检索结果，只改变上下文组装。这样可以隔离父块扩展的收益，也不需要重复向量化。

第一轮固定以下条件：

- 语料、评估集及 dev/test 划分。
- Embedding、Rerank 模型与配置。
- 回答模型与提示词。
- 各路召回和候选数量。
- 当前 `maxContextLength=6000` 的正文字符预算，并记录实际输入 token。

后续再单独探索预算变化，避免把「多塞了文字」误认为切片算法改进。

## 三、首版父块规则保持简单

现有切片方案中的短章节合并、多子块命中加分等策略，建议首版暂缓。

### 3.1 章节归属

- 短章节保留独立父块，先不跨章节合并。
- 当前 `chunking.ts` 会将不足 200 字的章节并入下一节，并把路径记为下一节，存在归属失真的问题；新方案应保留真实归属。
- 父块以连续章节区间为单位，不要只按 `sectionPath` 字符串分组，避免文章中的重复标题被合并。
- 长章节按段落边界分段，表格保留表头与行结构。

### 3.2 检索与排序

- 子块承担关键词检索、向量检索与 Rerank。
- 父块排序先使用最佳命中子块的分数。
- 暂不追加「同父块命中越多，加分越多」的策略，避免长章节因子块多而天然占优，也减少调参变量。
- 保留当前标题、章节、关键词前缀。
- 暂不引入 LLM 语义切分或逐块生成上下文。

首版只验证「小块定位、父块补证据」这一核心假设。

## 四、预算不足时优先保住命中证据

当前 `buildAnswerContext()` 在首块过长时直接从开头截取。换成父块后，如果命中子块位于父块末尾，截取开头可能把真正命中的证据删掉。

建议采用以下策略：

> 父块能放下则放全文；放不下则保留命中子块，再按原文顺序补充附近内容。

配套要求：

- 同一父块只进入上下文一次，多个命中区域去重。
- 明确区分检索候选数与最终上下文父块数，不要悄悄将已有 `topK` 从子块数改为父块数。
- 日志同时保存命中子块与实际送入模型的文本范围。
- 评估最终组装后的上下文，而不是只评估扩展前的检索结果。

这些信息用于解释「检索到了，回答为什么仍然遗漏」，也用于验证扩展是否挤掉其他必要证据。

## 五、评估不能只看文章命中率

保留现有方案中「文章 + 原文证据」的标注方式，不绑定切片 ID，确保切片改变后评估集仍然有效。

现有评估设计的 Evidence Hit 允许多段证据任一段命中。对于父子块，这不足以反映证据完整性：只检索到结论，却缺少前提或限制条件，也可能算成功。

建议分层报告：

| 层面 | 指标 | 目的 |
| --- | --- | --- |
| 找对文章 | 来源文章 Hit@5/@10、MRR | 检查检索是否退步 |
| 找到证据 | 子块阶段证据命中率 | 判断小块定位收益 |
| 补全证据 | 最终上下文证据覆盖率、必要证据全部覆盖率 | 判断父块扩展收益 |
| 实际回答 | 正确性、完整性、引用支持情况 | 防止上下文更长但回答更差 |
| 成本 | 实际输入 token、p95 延迟、索引规模 | 判断收益是否值得 |

「必要证据全部覆盖」需要在题目审核时确认哪些证据共同构成答案依据，不能把可互相替代的摘录都强制算作必要证据。

现有评估集是单来源合成标注，相关指标应继续明确标为来源文章命中指标，不据此宣称完整的全库召回率或生产问答质量。

### 上下文依赖专项题

补充并单独报告以下题目：

- 结论与成立条件分处相邻段落。
- 机制与实验结果分开描述。
- 表格数值需要结合正文解释。
- 回答需要同时引用多个必要证据片段。

专项题用于检测父块扩展的目标能力，不应为了体现父子块优势而改变主评估集的整体分布。

## 六、上线标准包含正收益

现有方案主要要求 Hit、MRR、Evidence Hit 不明显下降。这可以防回归，但不足以证明值得承担更多子块、索引重建和维护成本。

建议上线前同时满足：

- 文章检索指标总体稳定，关键题型没有明显退化。
- 完整证据覆盖或回答完整性有可重复的提升。
- 在相同上下文预算下仍有收益。
- 逐题检查新增成功与新增失败，确认不是少数题或语料变化导致。
- 使用逐题配对比较，并报告不确定性；小样本下不把 1 个百分点的差异解释成确定收益。
- 延迟、输入 token、索引规模等成本处于可接受范围。

开发集用于选参数，测试集只用于阶段验收。

## 七、复现与回退

基线至少保存：

- 语料快照与指纹。
- 数据集版本及 dev/test 划分。
- 代码版本、解析器与切片规则版本。
- 模型和检索配置，不包含密钥。
- 逐题检索结果、最终上下文、指标与失败信息。

旧索引保留可恢复快照，避免全量重切后无法可靠复现实验 A。改造期间不要将新旧切片混合状态下的结果作为正式对比结论。

## 八、推荐推进顺序

1. 完成可复现评估基线，冻结语料、数据集和实验 A 的结果。
2. 实现最小父子块结构与纯函数测试，重点检查章节归属、重复标题、长段落和表格。
3. 构建新子块索引，运行实验 B，确认小块定位效果。
4. 复用实验 B 的检索结果，运行实验 C，验证父块扩展和预算策略。
5. 检查整体指标、分组指标与逐题得失，补充回答层对比。
6. 在测试集完成阶段验收，收益明确后再决定上线。

首版不做短章节跨节合并、不做多命中加分、不增大上下文预算。将收益明确归因到「小块定位」和「父块补证据」，再决定是否增加更复杂的策略。
