# RAG 系统能力与缺失模块分析

评估日期：2026-10-25

评估范围：当前仓库中的数据处理、检索、问答、用户端、管理端、评估与部署相关实现。

评估方式：只读检查源码、调用链和测试代码，未运行在线效果评测或验证生产环境。本文描述的是本次检查时的实现状态；代码可能继续演进，行号仅供定位。

## 一、总体结论

系统已具备较完整的“文章知识库 RAG”基础闭环，并非仅有向量检索和聊天接口。

目前主要差距不在基础链路是否存在，而在以下方面：

- 多轮追问的检索理解。
- 知识更新、撤稿和失效管理。
- 在线证据充分性判断与引用校验。
- 用户反馈到回归评估的质量闭环。
- 已有父子块能力的线上验收与接入。
- 生产监控、备份恢复和发布保障。

需要区分“真正缺失”“已有实现但未接入线上”和“按业务定位扩展”，避免重复建设已有模块，或将高级架构误认为基础 RAG 的必备项。

## 三、优先补齐的能力

### 1. 历史感知检索

**状态：缺失。建议优先级：高。**

当前历史对话参与生成，但不参与检索。在线检索仍使用当前轮原始问题，没有先做指代消解或独立问题改写。

例如：

> 第一轮：介绍某种正极材料。
>
> 第二轮：它的循环寿命怎么样？

第二轮直接检索“它的循环寿命怎么样”，可能丢失材料名称。生成模型即使看得到历史，也无法保证检索阶段已经召回正确证据。

建议补充：

- 结合历史，将追问改写为可独立检索的问题。
- 保留原始问题用于回答，改写问题用于召回。
- 对实体不明确或存在歧义的问题进行澄清。
- 增加真实多轮追问的回归用例，验证改写是否保留实体、条件和约束。

依据：[在线检索调用](../apps/api/src/chat.ts#L72)、[历史对话与提示词组装](../packages/processing/src/rag.ts#L251)。

### 2. 知识更新与失效管理

**状态：已有增量同步，生命周期管理不完整。建议优先级：高。**

当前限制：

- 数据源同步频率已存储，但没有按频率自动创建同步任务。
- 完成回填后，连续若干页无变化就停止，可能漏掉列表深处的历史修订。
- 已知文章没有更新时间时，当前变化判断不会重新抓取。
- 缺少远端删除、撤稿后的本地对账与失效处理。

这可能造成检索和回答过程正常，但使用的知识已经过期或撤回。

建议补充：

- 按数据源频率调度同步，并防止重复任务。
- 定期进行覆盖历史数据的完整巡检。
- 制定删除、撤稿和权限撤销的对账规则。
- 失效内容退出检索，同时保留必要的历史追溯信息。
- 区分临时接口失败与确认删除，不能把一次抓取失败直接当作远端删除。

依据：[增量变化判断和扫描终止条件](../packages/processing/src/article/sync.ts#L63)、[Worker 周期任务](../apps/worker/src/index.ts#L338)。

### 3. 在线证据充分性与引用校验

**状态：有提示词约束和基础无命中处理，缺少在线质量门控。建议优先级：高。**

已有引用编号、来源摘录和“只依据资料回答”的提示词，但这些不等于答案已验证。

当前限制：

- 检索到内容，不代表内容足以回答问题。
- 向量相似度阈值不约束关键词召回结果。
- 缺少独立的证据充分性判断。
- 模型生成后，没有在线检查引用编号是否合法、关键结论是否有引用、引用是否支持结论。
- 离线引用评审已经存在，但没有形成线上门控。

建议分层建设：

1. 先实现低成本的引用编号合法性检查。
2. 明确证据不足时的拒答、部分回答或澄清策略。
3. 基于评估集校准相关性与证据充分性判断。
4. 对高风险回答按需增加结论与证据一致性核验。

不建议默认对所有请求追加一次昂贵的模型评审调用，应同时衡量效果、延迟和成本。

依据：[召回阈值与融合](../packages/processing/src/rag.ts#L97)、[回答生成与接受结果](../apps/api/src/chat.ts#L100)、[离线引用评估](../packages/processing/src/evaluation-answer.ts#L89)。

### 4. 用户反馈到回归评估的闭环

**状态：已有反馈采集和评估引擎，缺少运营工作流。建议优先级：高。**

目前有赞踩、问答日志和离线评估，缺的是将这些能力连接起来。

目标流程：

```text
用户差评或异常问答
  → 标记问题原因
  → 人工核查与证据标注
  → 脱敏、审核后纳入回归题集
  → 修改检索、切块或提示词
  → 回归评估与上线验收
```

建议补充：

- 反馈原因，如资料未召回、答案错误、引用不符、内容过时。
- 问题分类、处理状态和处理记录。
- 正确答案或正确证据的人工标注。
- 从线上坏例生成候选回归题的入口。
- 评估集覆盖多轮追问、跨文章比较、过滤条件和不可回答问题。

现有合成题集有价值，但明确不是来自真实用户且未经人工验证，不能替代真实业务题集。

依据：[反馈接口](../apps/api/src/chat.ts#L238)、[问答管理界面](../apps/admin/src/views/ChatLogsView.vue#L34)、[合成题集声明](../packages/processing/test/evaluation/nyz-rag-synthetic-v1.json#L2)。

### 5. 更完整的上下文组装

**状态：父子块及邻块扩展已有实现，未接入线上主链路。建议优先级：中。**

当前默认仍使用原切块方案，线上按命中切片组装上下文。父块及命中邻域组装代码已经存在，但需通过评估验收后再接入。

潜在收益：

- 补充命中片段前后的实验条件、限定语和定义。
- 保留表格前后说明，降低脱离上下文作答的风险。
- 同一父块内的多个命中合并展示，减少重复内容。

另一个不足是上下文预算：当前主要按资料正文字符数计算，尚不是覆盖系统提示词、历史、参考资料和输出预留的完整 Token 预算。

建议先对比检索及回答效果，再决定是否启用父子块；不能仅因代码已存在就直接切换线上默认方案。

依据：[默认切块版本及验收说明](../packages/processing/src/chunking.ts#L44)、[当前上下文组装](../packages/processing/src/rag.ts#L128)、[父块与邻块上下文组装](../packages/processing/src/rag.ts#L180)。

### 6. 生产监控与交付保障

**状态：已有基础部署和逐条日志，系统级保障仍需补充。建议优先级：对外服务前完成。**

已有回答模式、模型、检索耗时、首 Token 耗时、总耗时、Token 用量和召回分数等记录，但仓库内未见完整的以下能力：

- 请求及模型错误率、降级率、延迟分位数的聚合监控。
- Worker 存活、队列积压和任务异常告警。
- 模型调用成本汇总及预算管理。
- 数据库、Redis 依赖就绪检查。
- 自动化备份恢复及恢复演练。
- 自动化发布、质量回归门禁和回滚流程。

当前 `/health` 固定返回正常，不等于数据库、Redis 和 Worker 已就绪。成功问答记录也不能替代失败请求监控。

以上是仓库内的检查结果，不能据此断言外部运维平台也没有这些能力。

依据：[问答指标保存](../apps/api/src/chat.ts#L115)、[健康检查](../apps/api/src/common.ts#L130)、[Compose 部署](../docker-compose.yml#L23)。

## 四、按产品定位决定的扩展

| 模块 | 当前情况 | 需要建设的条件 |
| --- | --- | --- |
| 知识库内容隔离与资源级权限 | 知识库主要是检索参数和提示词配置，没有绑定独立文档范围；管理员功能权限不能替代资料权限 | 接入部门私有资料、多客户或不同授权内容时，属于上线前置项 |
| 多租户 | 当前以单实例共享语料为主，没有完整租户边界 | 对多个独立组织提供服务时 |
| PDF、附件、OCR、图表理解 | 当前限定文章 API，图片和附件内容不参与检索 | 关键证据在论文附件、实验曲线或扫描件中时 |
| 查询分解与多跳检索 | 当前主要为单次召回后生成 | 经常回答跨文章比较、组合证据和复杂研究问题时 |

### 知识库隔离的特别说明

当前知识库配置不代表独立语料空间。请求中的 `sourceId` 等过滤器可以缩小检索范围，但由客户端提供的过滤条件不能充当服务端授权边界。

如转向企业私有知识平台，应同时覆盖检索、搜索、文章详情和引用原文等访问路径，而不只是隐藏管理界面入口。

依据：[知识库表](../packages/processing/src/schema.ts#L213)、[在线检索接线](../apps/api/src/chat.ts#L57)、[检索过滤器](../packages/processing/src/retrieval-filters.ts#L8)。

### 多模态接入的特别说明

仅支持文章 API 是当前明确的产品边界，不宜直接称为“缺少数据接入模块”。如果文章正文已覆盖业务所需知识，可以暂不扩展文件上传和爬虫。

若证据主要位于图片、附件或图表中，现有文字检索无法覆盖这些内容，此时才需要优先建设相应解析和检索能力。

依据：[参与检索的内容范围](../packages/processing/src/chunking.ts#L279)。

GraphRAG、Agentic RAG、联网搜索和语义缓存不是基础 RAG 的必备模块。不建议仅为了架构完整而全部引入，应由真实失败案例、性能瓶颈和评估收益驱动。

## 五、建议实施顺序

针对当前文章知识库定位，建议按以下顺序推进：

| 阶段 | 建设内容 | 主要目标 |
| --- | --- | --- |
| 第一阶段 | 历史感知检索、定时同步、完整巡检和失效管理 | 解决追问检索不准、知识不新的问题 |
| 第二阶段 | 真实反馈闭环、回归题集、证据不足处理与引用校验 | 使质量问题可定位、可复现、可验收 |
| 第三阶段 | 父子块线上验收、完整 Token 预算 | 提升证据完整性并控制上下文开销 |
| 对外服务前 | 监控告警、依赖就绪检查、备份恢复和发布门禁 | 确保服务稳定且故障可恢复 |

若接入私有资料或多客户数据，应将知识库隔离、资源授权和租户边界提前至第一优先级。

## 六、结语与限制

系统不缺“能跑通的 RAG”，下一阶段应重点补齐“检索理解正确、证据足够、知识有效、质量可持续改进”。

本文不是性能报告或生产安全审计，也未实测回答质量。具体效果、吞吐、延迟、部署配置和外部运维能力，仍需通过对应测试与环境验证确认。
