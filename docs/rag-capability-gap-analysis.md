# RAG 系统能力与缺失模块分析

评估日期：2026-10-25

评估范围：当前仓库中的数据处理、检索、问答、用户端、管理端、评估与部署相关实现。

评估方式：初始评估为只读源码检查；第 2 项已随知识更新实现修订，第 3 项已随引用存在性/编号门控与回答策略实现修订，第 4 项已随反馈处理及审核导出工作流修订。验证范围为本地自动化测试（含 API mock 与本地 HTTP SSE 测试），未运行真实模型效果评测或验证生产环境。本文描述的是当前实现状态；代码可能继续演进，行号仅供定位。

## 一、总体结论

系统已具备较完整的“文章知识库 RAG”基础闭环，并非仅有向量检索和聊天接口。

目前主要差距不在基础链路是否存在，而在以下方面：

- 多轮追问的检索理解。
- 撤稿和失效管理（频率调度与全量详情巡检已实现）。
- 在线证据充分性与引用支持度判断（引用存在性/编号门控及提示词策略已实现，不等于答案已验证）。
- 真实反馈题集的人工运营与回归验收（反馈处理及审核导出入口已实现）。
- 已有父子块能力的线上验收与接入。
- 生产监控、备份恢复和发布保障。

需要区分“真正缺失”“已有实现但未接入线上”和“按业务定位扩展”，避免重复建设已有模块，或将高级架构误认为基础 RAG 的必备项。

## 三、优先补齐的能力

### 1. 历史感知检索

**状态：缺失。建议优先级：高。**

当前历史对话参与生成，但不参与检索。在线检索仍使用当前轮原始问题，没有先做指代消解或独立问题改写。

例如：

> 第一轮：介绍某种正极材料。
>
> 第二轮：它的循环寿命怎么样？

第二轮直接检索“它的循环寿命怎么样”，可能丢失材料名称。生成模型即使看得到历史，也无法保证检索阶段已经召回正确证据。

建议补充：

- 结合历史，将追问改写为可独立检索的问题。
- 保留原始问题用于回答，改写问题用于召回。
- 对实体不明确或存在歧义的问题进行澄清。
- 增加真实多轮追问的回归用例，验证改写是否保留实体、条件和约束。现有评估集全部为单轮合成题，这批用例需与改写同期建设，否则改写无法验收。
- 只在存在历史时改写；改写会多一次模型调用，需评估对首 Token 延迟和费用的影响。

依据：[在线检索调用](../apps/api/src/chat.ts#L72)、[历史对话](../packages/processing/src/rag.ts#L259)（`historyMessages`）与[提示词组装](../packages/processing/src/rag.ts#L277)（`buildChatMessages`）。

### 2. 知识更新与失效管理

**状态：频率调度与全量详情巡检已实现；自动失效被上游删除语义未确认阻塞，未交付。建议优先级：高。**

本次已实现：

- 引用校验可在管理端按知识库开关（`knowledge_bases.citation_check`，默认开启）。以下门控、严格提示词与谨慎摘录文案只在开启时生效；关闭时恢复引入门控之前的宽松提示词与摘录文案，模型回答非空即采用。`evaluate:answer` 按知识库开关选择提示词并记入运行参数（不做生成后门控）。2026-10-25 在 dev 集 238 题上的对比（语料快照不同）：开启后门控拦截 0 题，complete 通过率 97.5% → 96.6%，表示资料不足 1.3% → 2.1%，其中 1 题（s0022）因严格提示词过度拒答。

- Worker 启动及每 30 秒检查「运行中」来源，按「每小时 / 每 6 小时 / 每天」创建任务；暂停、手动、空值和未知频率不自动调度。首次从未同步的来源立即到期，停机后只补一个任务，不累积历史周期。
- 使用数据库最近任务创建时间与最近成功完成时间的较晚者作为周期起点，失败也消耗周期，避免每轮创建失败任务。长任务若失败时周期已过，允许下一轮到期重试；不会绕过后续新任务的周期。手动同步也重置周期，暂停不会取消已排队/运行的任务。
- 到期条件、当前来源状态与频率在来源行锁内复查，复用任务/outbox 事务及活动任务/操作唯一索引，防止并发 Worker 和手动触发重复创建。周期保存在现有数据库时间字段中，重启不丢失，不需要新增调度表。
- 首次回填完成后每 7 天，在后续同步任务中启动完整列表巡检；旧来源没有巡检时间时下次同步即启动。巡检不按静默页提前结束，重新请求全部列表文章详情，因此能刷新深处历史修订、未变化或缺少 `updateTime` 的文章。
- 全量巡检持久化页码及页内已尝试 key，在单次上限、异常或重启后续跑，即使预算小于一页也能前进；每篇尝试和每页完成保存断点。普通详情错误留待重试，不阻碍扫描；fatal 详情错误和列表错误保留断点且不标记完成。巡检优先于失败重试，避免重试耗尽预算而饿死历史扫描。

尚未交付及限制：

- **自动删除、撤稿、权限撤销的对账与退出检索没有实现。** 未获得 nyzdata 对这些事件的权威、可区分语义，不能自行约定「列表消失」或「404」就是删除。确认接口契约是前置阻塞，不是可用猜测绕过的实现细节。
- 列表缺席、总数减少、404、权限问题、超时或其他接口错误均不自动失效、删除或清空现有正文/切片/向量。保留现有知识可避免误删，但已撤回的文章可能继续参与检索，需管理员确认并人工处理。
- 巡检完成时间只证明列表遍历结束，不代表全部详情刷新成功或远端删除已确认；失败 key 继续保留（最多 500 个，超出部分依靠后续巡检重新发现）。
- 分页接口没有一致性快照保证，列表在巡检中重排仍可能遗漏或重复；7 天是下一次巡检的启动间隔，不是所有文章刷新的硬性时效 SLA。大来源受频率和单次上限限制可能跨多个周期；手动来源需要手动续跑。
- 全量详情刷新沿用现有重新解析、切片和向量化路径，可能增加请求与模型费用；普通增量仍依赖 `updateTime`，缺失时间戳的刷新由全量巡检兜底。

后续需要先确认上游删除/撤稿/权限契约，再设计可审计、可恢复的失效状态及所有检索/详情路径的过滤规则。不能把一次抓取失败当作删除，也不能仅因遍历结束就执行缺席失效。

依据：[任务创建与频率调度](../packages/processing/src/repository.ts)（`createTask`、`scheduleDueSources`）、[增量与全量巡检](../packages/processing/src/article/sync.ts)、[Worker 周期任务](../apps/worker/src/index.ts)、[同步状态](../packages/types/src/index.ts)（`ArticleSourceSyncState`）、[数据库并发/周期/错误安全测试](../packages/processing/test/operations.test.ts)、[巡检恢复单元测试](../packages/processing/test/article.test.ts)。

### 3. 在线证据充分性与引用校验

**状态：第一层引用存在性/编号门控与提示词策略已实现；语义证据充分性与引用支持度判断未实现。后续建议优先级：高。**

已有引用编号、来源摘录和“只依据资料回答”的提示词。本次增加低成本的生成后门控，但引用编号合法仍不等于答案已验证。

本次已实现：

- 将 `citedNumbers` / `citationStats` 提取至无运行时依赖的纯函数模块 `citations.ts`，保留离线评估原有导出。离线统计与在线门控共用 `validateCitations` 的解析及越界检查，支持 `[1]`、`[1][2]`、`[1, 2]`、`[1，2]`、`[1、2]`，检查范围为本轮送入上下文的文章编号。
- `/api/chat` 与会话 SSE 共用生成接受逻辑：存在越界编号（包括 `[0]`）或没有可识别引用时不接受生成回答，降级为明确谨慎的原文摘录。摘录明确标注未验证其是否足以回答问题、不代表已核实答案，仍使用 `extractive` 模式，不冒充已验证回答。
- 无引用只允许固定拒答 `参考资料不足以回答该问题，请补充问题中的对象、条件或相关资料。`；对去除首尾空白后的完整回答做精确匹配，不按关键词或子串放行。提示词要求无法作答或必须先澄清时仅输出该句。
- 提示词明确部分回答策略：只答有依据的部分并引用，列明未能回答的部分；对象、条件、指代不明确时不得猜测，有部分依据时可附具体澄清请求，完全无法作答时使用固定拒答。这些是模型行为约束，不是程序对策略遵循情况的语义验证。
- SSE 边生成边发送模型输出（`token` 事件），`done` 事件中的回答为准：生成完成后门控未通过或模型在部分输出后失败时，`done` 携带谨慎摘录替换已显示的文本（被拒绝的片段会短暂显示）。末尾未写完的引用编号（如 `[1、`）暂缓发送；一旦出现越界编号即停止读取模型流并降级，越界编号本身不会发给客户端，此时拿不到供应商的 usage 统计。尚未发出任何模型输出时，最终回答作为一个 `token` 事件发送。`AdmissionError` 仍返回错误、不降级、不保存；客户端断开仍中止模型调用并丢弃本轮结果。
- 此门控不增加模型评审调用，也未引入新相关性阈值，不增加可见首 Token 延迟。在线 `firstTokenMs` 记录 SSE 首次发送回答文本的时间（模型首段输出，或未调用模型时的摘录），不论该输出最终是否被接受；非 SSE 响应不记录首 Token 指标。

当前限制：

- 检索到内容，不代表内容足以回答问题。
- 向量相似度阈值只作用于两路向量召回，不约束关键词召回结果；Rerank 后直接取前 topK，也没有分数门槛。只要关键词命中一个词项，切片就可能进入上下文并触发生成。
- 缺少独立的语义证据充分性判断，也没有基于评估集校准的相关性/充分性阈值。
- 门控仅检查回答整体有无可识别引用与其编号是否合法，不检查每个关键结论是否有引用、引用是否支持结论，不能发现“编号正确但内容无关”或断言缺乏依据的问题。
- 固定拒答是否适当、部分回答是否完整、是否应当澄清仍由生成模型判断，未提供程序级语义保证。无命中仍沿用原有固定提示，不调用生成模型。
- 离线模型引用评审仍是离线能力，未作为在线语义门控，也没有追加昂贵的 judge 调用。

后续分层建设：

1. 用真实失败案例与人工标注评估固定拒答、部分回答及澄清策略的效果，统计流式输出后被 `done` 替换为摘录的比例。
2. 基于评估集校准相关性与证据充分性判断，不能自行假设一个通用分数门槛。
3. 对高风险回答按需增加结论与证据一致性核验。

不建议默认对所有请求追加一次昂贵的模型评审调用，应同时衡量效果、延迟和成本。

依据：[召回与提示词策略](../packages/processing/src/rag.ts)（`retrieve`、`buildChatMessages`、`extractiveAnswer`）、[回答生成与接受门控](../apps/api/src/chat.ts)（`answerQuestion`）、[共享引用校验](../packages/processing/src/citations.ts)、[离线统计兼容导出](../packages/processing/src/evaluation-answer.ts)、[引用统计测试](../packages/processing/test/evaluation-answer.test.ts)、[提示词与摘录测试](../packages/processing/test/retrieval.test.ts)、[API mock 与 SSE 流式/断开测试](../apps/api/test/chat.test.ts)。自动化测试验证机械规则与传输行为，不证明真实回答质量或语义证据充分性。

### 4. 用户反馈到回归评估的闭环

**状态：反馈处理、人工标注及审核导出工作流已实现；真实业务标注题集与效果验收仍需运营建设。建议优先级：高。**

在原有赞踩、问答日志和离线评估基础上，增加用户反馈原因、可修改/撤销的评价，以及管理端差评筛选、处理记录和人工回归候选题。用户评价与管理员核查结论分别记录，差评不会自动成为标准答案。

工作流：

```text
用户差评或异常问答
  → 标记问题原因
  → 人工核查与证据标注
  → 脱敏、审核后纳入回归题集
  → 修改检索、切块或提示词
  → 回归评估与上线验收
```

本次实现：

- 管理端支持好评、差评、已评价、未评价筛选，并在问答详情处理问题分类、状态和记录。
- 用户可修改或撤销评价，并提供资料未召回、答案错误、引用不符、内容过时等原因。
- 人工编写候选题、参考答案及文章证据，不自动复制原始模型回答作为标准答案，也不推断日志中未保存的历史和过滤条件。
- 保存采用版本检查；修改后原审核批准失效。审核和导出需要独立于查看权限的管理权限，导出仅允许当前已批准版本。
- 导出采用评估字段白名单，不序列化原始问答日志、账号、会话或内部处理备注。人工须确认所有候选字段已脱敏；白名单不是自动识别个人信息的保证。
- 批准和导出时核对文章外部 ID 唯一对应当前就绪、非重复文章，并检查证据经 NFKC/空白归一化后确实存在于当前文章内容。此检查证明摘录存在，不证明其支持标注结论。

尚未完成及限制：

- 没有凭空建立或宣称已验证的真实业务题集；仍需业务人员持续核查、标注、审核并执行效果回归。合成题集不能替代真实用户问题。
- 候选数据格式可表达跨文章比较、多轮历史、过滤条件和不可回答问题，但现有评估执行器尚不能正确重放带历史或过滤条件的题目；这些输入显式拒绝运行，不能静默忽略后报告成功。历史感知检索仍见第 1 项。
- 不可回答题的收录不等于已建立专门的拒答质量指标或上线门禁；自动发布验收、双人独立标注及裁决仍未实现。
- 当前每次导出一条已批准候选题，尚无批量合并、跨题去重或正式题集发布管理。

此流程提供从坏例到审核候选题的工具，不自动证明参考答案正确、证据语义充分或真实回答质量提高。

依据：[反馈与管理接口](../apps/api/src/chat.ts)、[反馈及审核持久化](../packages/processing/src/repository.ts)、[问答筛选](../apps/admin/src/views/ChatLogsView.vue)、[详情处理界面](../apps/admin/src/views/ChatLogSheet.vue)、[评估格式](../packages/processing/src/evaluation.ts)、[合成题集声明](../packages/processing/test/evaluation/nyz-rag-synthetic-v1.json#L2)。

### 5. 更完整的上下文组装

**状态：父子块及邻块扩展已有实现，未接入线上主链路。建议优先级：中。**

当前默认仍使用原切块方案，线上按命中切片组装上下文。父块及命中邻域组装代码已经存在，但需通过评估验收后再接入。

潜在收益：

- 补充命中片段前后的实验条件、限定语和定义。
- 保留表格前后说明，降低脱离上下文作答的风险。
- 同一父块内的多个命中合并展示，减少重复内容。

另一个不足是上下文预算。输出上限已有（业务模型的最大 Token 作为 `max_tokens` 传给模型），但输入侧只按参考资料正文字符数计算，系统提示词和历史（固定 3 轮、每轮回答截断为 500 字）不计入，尚不是按 Token 计算的完整输入预算。

建议先对比检索及回答效果，再决定是否启用父子块；不能仅因代码已存在就直接切换线上默认方案。

依据：[默认切块版本及验收说明](../packages/processing/src/chunking.ts#L44)、[当前上下文组装](../packages/processing/src/rag.ts#L128)、[父块与邻块上下文组装](../packages/processing/src/rag.ts#L180)。

### 6. 生产监控与交付保障

**状态：已有基础部署和逐条日志，系统级保障仍需补充。建议优先级：对外服务前完成。**

已有回答模式、模型、检索耗时、首 Token 耗时、总耗时、Token 用量和召回分数等记录，但仓库内未见完整的以下能力：

- 请求及模型错误率、降级率、延迟分位数的聚合监控。
- Worker 存活、队列积压和任务异常告警。
- 模型调用成本汇总及预算管理。
- 数据库、Redis 依赖就绪检查。
- 自动化备份恢复及恢复演练。
- 自动化发布、质量回归门禁和回滚流程。

当前 `/health` 固定返回正常，不等于数据库、Redis 和 Worker 已就绪；Compose 中 web、admin 依赖 api 的健康状态，因此这项依赖实际不起作用。Worker 没有配置健康检查。仓库中也没有 CI 工作流和指标暴露接口。成功问答记录不能替代失败请求监控。

以上是仓库内的检查结果，不能据此断言外部运维平台也没有这些能力。

依据：[问答指标保存](../apps/api/src/chat.ts#L115)、[健康检查](../apps/api/src/common.ts#L131)、[Compose 部署](../docker-compose.yml#L23)。

## 四、按产品定位决定的扩展

| 模块 | 当前情况 | 需要建设的条件 |
| --- | --- | --- |
| 知识库内容隔离与资源级权限 | 知识库主要是检索参数和提示词配置，没有绑定独立文档范围；管理员功能权限不能替代资料权限 | 接入部门私有资料、多客户或不同授权内容时，属于上线前置项 |
| 多租户 | 当前以单实例共享语料为主，没有完整租户边界 | 对多个独立组织提供服务时 |
| PDF、附件、OCR、图表理解 | 当前限定文章 API，图片和附件内容不参与检索 | 关键证据在论文附件、实验曲线或扫描件中时 |
| 查询分解与多跳检索 | 当前主要为单次召回后生成 | 经常回答跨文章比较、组合证据和复杂研究问题时 |

### 知识库隔离的特别说明

当前知识库配置不代表独立语料空间。请求中的 `sourceId` 等过滤器可以缩小检索范围，但由客户端提供的过滤条件不能充当服务端授权边界。

如转向企业私有知识平台，应同时覆盖检索、搜索、文章详情和引用原文等访问路径，而不只是隐藏管理界面入口。

依据：[知识库表](../packages/processing/src/schema.ts#L213)、[在线检索接线](../apps/api/src/chat.ts#L72)、[检索过滤器](../packages/processing/src/retrieval-filters.ts#L4)。

### 多模态接入的特别说明

仅支持文章 API 是当前明确的产品边界，不宜直接称为“缺少数据接入模块”。如果文章正文已覆盖业务所需知识，可以暂不扩展文件上传和爬虫。

若证据主要位于图片、附件或图表中，现有文字检索无法覆盖这些内容，此时才需要优先建设相应解析和检索能力。

依据：[参与检索的内容范围](../packages/processing/src/chunking.ts#L283)（`articleChunkBlocks`）。

GraphRAG、Agentic RAG、联网搜索和语义缓存不是基础 RAG 的必备模块。不建议仅为了架构完整而全部引入，应由真实失败案例、性能瓶颈和评估收益驱动。

## 五、建议实施顺序

针对当前文章知识库定位，建议按以下顺序推进：

| 阶段 | 建设内容 | 主要目标 |
| --- | --- | --- |
| 第一阶段 | 历史感知检索及配套的多轮回归题、失效管理（接口删除语义仍阻塞）；差评筛选及反馈处理入口、定时同步、完整详情巡检、引用存在性/编号门控与拒答/部分回答/澄清提示词策略已实现 | 解决追问检索不准、知识失效问题；已交付门控只覆盖机械引用规则，不代表完成语义质量保障，SSE 流式输出时被拒绝的文本会短暂显示后被替换 |
| 第二阶段 | 运营审核导出流程，积累真实回归题集；补齐多轮/过滤条件评估重放、回答策略效果验收、基于标注校准的证据充分性判断与按需引用支持度校验 | 使质量问题可定位、可复现、可验收，不把工作流交付当成真实质量验收，不把提示词策略当成语义验证 |
| 第三阶段 | 父子块线上验收、完整 Token 预算 | 提升证据完整性并控制上下文开销 |
| 对外服务前 | 监控告警、依赖就绪检查、备份恢复和发布门禁 | 确保服务稳定且故障可恢复 |

若接入私有资料或多客户数据，应将知识库隔离、资源授权和租户边界提前至第一优先级。

## 六、结语与限制

系统不缺“能跑通的 RAG”，下一阶段应重点补齐“检索理解正确、证据足够、知识有效、质量可持续改进”。

引用存在性/编号门控与回答策略已交付第一层保护，但不能据此声称已实现语义证据充分性、逐项结论验证、引用支持度验证或经校准的阈值判断。

本文不是性能报告或生产安全审计，也未实测回答质量。具体效果、吞吐、延迟、部署配置和外部运维能力，仍需通过对应测试与环境验证确认。
