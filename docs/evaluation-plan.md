# 检索评估集方案：文章派生合成基线

状态：生成（G）、评估（A）、对比（B）与失败题复判（H，第 7.3、8.9 节）已实现，`nyz-rag-synthetic-v1` 已冻结（第 5.5 节），dev 集基线已运行（第 8.4 节）；实验索引（第 8.5 节）与父子块切片实验（第 8.6 节）已完成，父子块暂不上线；回答层评估（第 8.7 节）已实现，dev 集基线已运行（第 8.8 节）。目标是在没有人工标注资源的条件下，由 AI 按文章生成带原文证据的问题，建立可重复运行的检索回归基线，作为切片、检索、Rerank 等调整的对比依据。[切片改造](chunking-design.md)以本基线验收。

## 一、定位与边界

- **这是合成题，不是真实问题**：问题由 AI 根据单篇文章生成，参考答案与证据来自原文，经程序校验和 AI 审核，没有人工标注。数据集标记 `source=synthetic`，指标单独报告，不与将来的真实问题集合并，不用于宣称生产问答质量或用户满意度。
- **单来源标注**：每道题只确定「生成它的来源文章」和「原文证据」两项。其他文章也可能回答同一问题，但首版不判定，因此不报告完整 Recall、nDCG 和上下文精度，只报告与来源文章相关的指标（第七节）。
- **用途**：比较同一语料上不同切片、Embedding、检索路径、融合与 Rerank 配置的相对变化。合成题系统性偏向「问题措辞接近原文」，绝对数值偏乐观，以两次运行的差值和逐题名次变化为主要依据。
- **评估真实链路**：直接调用问答使用的 `retrieve()`（关键词 + 子块向量 + 摘要召回、RRF、Rerank），并能逐路消融。
- **标注不随切片变化**：生成题目时使用完整正文，不参考当前切片；标注到「文章 + 证据原文」，不记录切片 ID。切片方案改变后数据集仍然有效。
- **检索只输入问题**：参考答案与证据只用于校验题目质量和计算证据命中，检索时不得带入。
- **防止过拟合**：按文章固定划分 dev / test，调参只看 dev，test 只在阶段验收时运行。

## 二、前置条件

1. **全量语料入库**：在管理后台配置 nyzdata token 并完成全量同步，在模型配置中选择 Embedding 模型并完成向量化。以数据库中的实际文章数为准，不沿用估算的「约 7068 篇」。
2. **评估语料范围**：文章接口来源、`status = ready`、非重复（`duplicate_of IS NULL`，处理状态不是 `duplicate`）的主文档。向量化未完成的文章计入覆盖率报告；覆盖率不足 100% 时，hybrid 模式的运行结果标记为不完整。
3. **生成与审核模型可用**：生成使用业务模型中的 Chat 模型，审核使用业务模型中的「审核」模型（`review`，温度建议为 0）。审核模型建议与 Chat 选用不同的模型，避免同一模型审核自己生成的题目；未配置审核模型时命令报错，不退回 Chat 模型。
4. **评估用知识库参数固定**：`topK`、`similarityThreshold`、`rerankEnabled`、`maxContextLength` 写入每次运行记录。比较两次运行时只改变待验证的变量。

## 三、语料快照与抽样

### 3.1 语料快照

生成开始时冻结语料快照，写入数据集的 `corpus` 字段：

| 字段 | 内容 |
| --- | --- |
| `documents` | 符合第二节范围的文章数 |
| `fingerprint` | 按 `articleKey` 排序的 `articleKey:content_hash` 列表的 SHA-256。切片或向量变化不影响它，正文变化才会改变 |
| `parserVersions` | `parser_version` 的分布 |
| `chunkerVersion` | 切片规则版本（`CHUNKER_VERSION` 引入前为空） |
| `embeddingModel` / `embeddingCoverage` | 默认 Embedding 模型与已向量化文章的比例 |

评估运行时重新计算指纹。与数据集不一致时给出警告，并逐题检查：来源文章已不在语料中，或证据已不在原文（`metadata` 题含标题与元数据线索）中的题目列出并排除在指标之外。冻结的数据集不保存逐篇的 `content_hash`，因此以证据是否仍在原文中判断，正文改动未涉及证据的题目仍然有效。

### 3.2 抽样

不做一篇一题的全量覆盖。原因是每次运行的查询 Embedding、Rerank 调用和耗时都与题数成正比，消融和反复对比时成本会成倍增加。300～400 道题时 Hit@10 的标准误约 2～3 个百分点；同一批题目在两次运行间做逐题配对对比，比单独看两个绝对值更灵敏，足以分辨改动效果。

- **样本量**：首版抽 400 篇，按约 85% 的通过率预计得到约 340 道题；语料增长后按版本扩充到约 600 篇。
- **排除**：正文不足 300 字的文章（以图片为主，没有可出题的文字）。
- **分层**：按栏目（`category`，样本不足 20 篇的栏目合并为「其他」）、科研栏目内标题是否识别出期刊（`metadata.titleMeta.journal`），以及正文长度三分位分层，按比例抽样。不按发布年份分层，因为现有语料 97% 发布于 2026 年。

2026-10-23 的业务库语料情况：

- **文章数**：主文档 1126 篇，其中 1125 篇已向量化，使用 `BAAI/bge-m3`、1024 维；共 6940 个切片。
- **栏目分布**：科研 597 篇（其中 503 篇识别出期刊），能学堂 271、供应链 67、能人堂 59、排行榜 43、储能系统 43，其余栏目合计不足 50 篇。
- **正文长度**：中位 3390 字，P90 5115 字，最长 2.8 万字；不足 300 字的 4 篇。
- **元数据**：有关键词的 803 篇，标题识别出机构的 388 篇，有项目负责人的只有 37 篇。

**语料增长**：同步仍在进行时，已有题目在文章不变的情况下依然有效，但语料指纹会变，基线运行需要在新语料上重跑；不需要重新生成题目。文章越多，干扰项越多，指标会自然下降，不同语料快照上的运行不能直接比较（`evaluate:compare` 会给出警告）。
- **可复现**：抽样使用固定随机种子，种子与分层规则写入数据集的 `sample` 字段。

### 3.3 划分

按 `articleKey` 的 SHA-256 取模确定 `split`：dev 约 2/3，test 约 1/3。同一篇文章的题目始终落在同一侧。以后扩充时，已有文章的划分不变。

## 四、题目生成

### 4.1 输入

每篇文章调用一次生成，输入为标题、完整清洗正文（`documents.content`，正文中位约 4000 字、最长约 2.1 万字，无需截断）、元数据（关键词、项目名称、负责人、承担单位、标题识别出的期刊与机构），以及预先分配的题型与具体度。

### 4.2 题型与具体度

抽样后为每篇文章预先分配目标题型与具体度，以控制整体分布。不满足条件的文章，生成器可以退回 `fact`，退回会被记录。

| 类型 `type` | 目标占比 | 说明 | 分配条件 |
| --- | --- | --- | --- |
| `fact` | 40% | 单篇事实：数值、结论、方法 | 任意文章 |
| `mechanism` | 25% | 机制、原因、作用 | 正文含机制或原因论述 |
| `metadata` | 20% | 以机构、期刊、负责人、项目为线索找文章 | 有对应元数据 |
| `term` | 15% | 化学式、材料名、术语的精确匹配 | 正文含化学式或专有术语 |

| 具体度 `specificity` | 目标占比 | 要求 |
| --- | --- | --- |
| `high` | 约 68% | 可以使用原文的专有名词，但不得照抄句子；元数据题与术语题依赖原文专有名词，固定为 high |
| `low` | 约 32% | 用描述性或上位说法提问，不出现原文中的材料名、化学式、数值、机构名和人名，模拟不熟悉原文措辞的用户；事实题与机制题各一半为 low |

`low` 题天然可能被多篇文章回答，单来源 Hit 会偏低，所以必须与 `high` 题分开报告（第七节）。

首版不生成 `compare`（需跨篇标注）、`followup`（合成的多轮追问不像真实用户），也不生成 `unanswerable`（无法证明语料中确实没有答案）。

### 4.3 生成要求

输出 JSON：`question`、`answer`、`evidence[]`（1～3 段原文，每段不超过 200 字）、`type`、`specificity`。提示中写明以下要求：

- 问题能独立理解：不出现「本文」「该研究」「上述」「作者」等指代；
- 问题不照抄标题或证据句，不把答案写进问题；
- 问题指向这篇文章特有的内容（这项研究、产品、专利、报告或人物的具体数据、方法与结论），不问教科书通识或多数文章都会提到的常识，也不问「这篇文章讲了什么」；
- 不在问题中使用专利号、DOI、文章编号等用户通常不知道的标识符；
- 价格、行情、周报月报、装机或销量、排行榜、政策动态等时效性内容，问题必须写明时间范围，优先取自标题或正文，没有时按发布日期写（提示的文章头含发布日期）。否则同系列其他时期的文章也能回答；
- `low` 题用领域通用说法，自然直白，不写成刻意回避名称的谜语式描述；时间范围不算具体数值。人物或企业介绍类文章，问不依赖姓名也能自然表述的内容，不用身份描述代替姓名去问个人经历；
- 问题像真实业务人员会问的问题，长度 10～60 字；
- 证据必须逐字摘自正文（`metadata` 题可摘自元数据字段），答案只能依据证据，不得补充原文没有的内容。

## 五、校验与审核

### 5.1 程序校验

| 检查 | 规则 |
| --- | --- |
| 结构 | 字段齐全，类型与具体度合法，长度在范围内 |
| 证据存在 | 规范化（NFKC、去空白）后，每段证据都是正文的子串；`metadata` 题也可以是元数据字段的子串 |
| 指代与泄漏 | 不含禁用指代词；答案中的关键数值或短语不出现在问题里（年份除外，它是时效性问题应写明的时间范围） |
| 词面重叠 | 用 `searchTerms` 计算问题词项与「证据 + 标题」词项的重叠率，写入 `lexicalOverlap`。`low` 题超过 0.5、`high` 题超过 0.8 时打回（初始阈值，试点后调整） |
| 重复 | 与已通过题目的问题词项 Jaccard ≥ 0.6 时打回 |

### 5.2 AI 审核

使用审核模型独立调用一次，输入完整正文、问题、答案和证据。审核员先写一段 `analysis`，分析同系列或同主题的其他文章（其他时期的周报、同一材料的其他研究、同一企业的其他报道）能否同样回答、是否属于通识，再逐项打 1～5 分并说明理由：

- `standalone`：不看文章也能理解问题在问什么（时效性内容缺少时间范围也算不能独立理解）；
- `supported`：证据足以支持答案；
- `faithful`：答案没有编造或过度推断；
- `specific`：问题有明确答案，不是开放式讨论；
- `distinctive`：问题指向这篇文章特有的内容，不是多数同类文章都能回答的通识。单来源标注只认来源文章，通识题会把其他能回答的文章判为错误；
- `natural`：措辞像真实提问，不是对原文的改写，不是谜语式描述，不含用户通常不知道的标识符。

每项都不低于 4 分（`REVIEW_PASS_SCORE`）才算通过，分数缺失或不合法视为不通过。前两版用布尔判断，审核几乎不拒题，第 3 版改为先分析再打分。`report.json` 记录已通过题目的各项平均分，预览中附每题得分与分析，用于观察审核口径。

### 5.3 重试与状态

每篇文章的状态依次为 `pending` → `generated` → `checked` → `approved`，或最终为 `rejected`。程序校验或审核未通过时，把失败原因反馈给生成器重试，最多 3 次。仍未通过的标记 `rejected` 并保留原因，不为凑数收入坏题。

工作文件放在 `.nyz-data/evaluation/<数据集名>/`（gitignored）：

- `sample.json`：语料快照、抽样结果，以及每篇文章的目标题型、具体度和正文指纹；
- `items.jsonl`：每篇文章每次尝试的生成、校验、审核结果和 token 用量，只追加不修改；
- `report.json`：本次范围内的通过率、失败原因、词面重叠分布和用量；
- `preview.md`：逐题预览，供人工浏览。

命令中断后从未完成的文章继续，已有结果不重复调用模型。模型调用失败（网络错误、供应商过载、审核输出无法解析）先退避重试 2 次，仍失败则记为 `error`，不计入尝试次数，下次运行重新处理。样本文章的正文在抽样后发生变化或被删除时，该文章记为 `stale` 并跳过。

### 5.4 试点

先抽 50 篇试生成，检查以下各项：

- 通过率与失败原因分布；
- 词面重叠分布；
- 重复率；
- 模型调用量与 token 用量；
- 开发者浏览约 20 道题，凭直觉判断是否像真实提问。

据此调整提示和阈值，提示版本号（`SYNTHETIC_PROMPT_VERSION`）随之提升。提升后，旧版本的记录保留在 `items.jsonl` 中但不再计入，样本文章用新提示重新生成，因此冻结的数据集只包含同一版本提示生成的题目。之后再扩展到全部样本。

第 1 版试点（2026-10-23，50 篇）的结果：

- 生成：通过 48 篇、拒绝 1 篇，通过的题平均尝试 1.3 次；失败原因主要是词面重叠过高。
- 审核：49 次审核只拒绝了 1 次，明显偏宽。
- 问题：浏览后发现三类问题审核都没有拦下——通识题（如 LiC₆ 的理论容量）、为避开原文用词写成谜语的 low 题、问题中出现专利号。
- 调整：第 2 版提示补充了上述要求，审核新增 `distinctive` 一项。
- 稳定性：审核供应商约 18% 的调用在流中返回过载错误，记为 `error` 后补跑即可完成。

第 2 版试点（同一批 50 篇）的结果：

- 生成：通过 48 篇、拒绝 2 篇，通过的题平均尝试 1.2 次。
- 词面重叠：低于 0.4 的 18 题、0.4～0.6 的 20 题、不低于 0.6 的 10 题。
- 用量：生成输入约 16 万、输出约 9 万 token；审核输入约 15 万、输出约 0.5 万 token。
- 改善：专利号和教科书通识题已消失，谜语式的 low 题减少。
- 遗留问题：
  - 审核仍然一题未拒，过滤主要靠生成提示和程序校验；
  - 行情周报类问题没有写明时间范围（如「DTD 的价格运行态势」），同系列的其他周报也能回答；
  - 人物介绍类 low 题仍有谜语式写法。

第 3 版（审核改为先分析再打分，时效性内容须写明时间范围，人物介绍类 low 题不用身份描述代替姓名；审核模型换为 gpt-6-luna）试点结果：

- 生成：通过 46 篇、拒绝 4 篇，通过的题平均尝试 1.4 次。
- 审核：拒绝 13 次，其中 12 次因为 `distinctive` 低于 4 分（通识题、同主题文章也能回答），审核开始起作用。
- 遗留问题：标题和正文都没有日期的周报（如「“金九”临近，电解液原料涨势再扩大」）仍然生成了不带时间的报价题，审核也放行了。

第 4 版（提示的文章头加入发布日期，没有其他时间时按发布日期写时间范围）试点结果：

- 生成：通过 46 篇、拒绝 4 篇，通过的题平均尝试 1.35 次。
- 审核：拒绝 10 次，其中 9 次因为 `distinctive`；已通过题目的平均分 `distinctive` 4.67，`natural` 4.8，其余各项接近 5。
- 时效性：行情类问题都写明了时间（如「2026年8月下旬，六氟磷酸锂的报价维持在什么区间？」）。
- 词面重叠：低于 0.4 的 14 题、0.4～0.6 的 21 题、不低于 0.6 的 11 题。
- 用量：生成输入约 19 万、输出约 11 万 token；审核输入约 19 万、输出约 2 万 token（审核需要先写分析，输出比第 2 版多）。
- 遗留问题：
  - `low` 题更容易被拒：被拒的 4 篇中 3 篇是 `low`，通过的题中 `low` 只占 22%，低于目标的约 32%。冻结前按具体度分别报告，不混算。
  - 带日期的 `low` 题，日期本身会与标题重叠，词面重叠更容易超限（如磷酸铁锂周报一题）。

第 4 版换审核模型重跑（审核改为 gpt-6.1-sol，旧记录存档后同一批 50 篇重新生成）：

- 生成：通过 42 篇、拒绝 8 篇，通过的题平均尝试 1.5 次；审核拒绝 24 次，其中 20 次因为 `distinctive`，比 gpt-6-luna 更严。
- 具体度：被拒的 8 篇全部是 `low`，通过的题中 `low` 只有 6 道（14%），`mechanism/low` 为 0。`low` 要求不出现文章特有的名称和数值，问题越泛化，同主题的其他文章越可能也能回答，与单来源标注要求的 `distinctive` 天然冲突。
- 用量：生成输入约 24 万、输出约 12 万 token；审核输入约 22 万、输出约 3 万 token。

决定不再调整提示，按第 4 版直接生成全量，`low` 题按具体度分开统计、只作参考。

### 5.5 全量生成（第 4 版，2026-10-23）

400 篇（含试点 50 篇）用 deepseek-flash 生成、gpt-6.1-sol 审核，并发 3，约 2 小时：

- 结果：通过 350 篇、拒绝 50 篇（87.5%），通过的题平均尝试 1.38 次；1 篇 `term` 回退为 `fact`。调用失败 13 次（供应商在流中报错），重新运行后全部补齐。
- 按目标：`term/high` 57/60、`fact/high` 71/72、`metadata/high` 73/80、`mechanism/high` 50/58、`fact/low` 70/88、`mechanism/low` 29/42。通过的题中 `low` 99 道（28%），比试点的 14% 高，试点 50 篇的比例偏差较大。
- 按栏目：科研 199/212、能学堂 80/97、供应链 20/23、储能系统 14/16、其他 14/16、排行榜 11/15、能人堂 12/21。能人堂（人物专访）通过率最低，`low` 题难以在不点名的情况下只指向一篇文章。
- 词面重叠：<0.4 有 97 道、0.4～0.6 有 170 道、≥0.6 有 83 道。
- 失败原因（按尝试计）：审核未通过 132 次（127 次因为 `distinctive`）、词面重叠过高 62 次、问题长度 50 次、证据不在原文中 15 次、格式错误 13 次。
- 通过的题审核平均分：`distinctive` 4.78、`natural` 4.85，其余均在 4.9 以上。
- 用量：生成输入约 170 万、输出约 94 万 token；审核输入约 159 万、输出约 18 万 token。
- 被拒的 50 篇不进入数据集（见 5.3），能人堂、能学堂的题数因此比抽样比例略少。
- 冻结为 `packages/processing/test/evaluation/nyz-rag-synthetic-v1.json`：350 道题，dev 238 道（`low` 67）、test 112 道（`low` 32）。

## 七、指标

### 7.1 排名列表与回答上下文

线上 `retrieve()` 只返回 `topK`（默认 5）个切片，不能直接当作前 10 篇文章的排名。评估时区分两份列表：

- **排名列表**：以 `topK = 30`（合并后的候选上限）调用 `retrieve()`。开启 Rerank 时，Rerank 的 `topN` 也随之为 30；Rerank 对每个切片独立打分，前 5 名与 `topN = 5` 时相同。切片按名次依次取所属文章、去重，得到文章排名。候选不足 10 篇文章的题目计入「排名深度不足」并单独报告。
- **回答上下文**：由 `--context` 选择组装方式，三种方式使用同一份排名列表：
  - `topk`（默认）：取排名列表前 `知识库 topK` 个切片，经 `buildAnswerContext(…, maxContextLength)` 截取，与线上进入模型的内容一致；
  - `budget`：按排名依次放入切片，直到 `maxContextLength`。切片长度不同的规则在 `topk` 下送入的字数不同，比较切片规则时用它统一字数预算；
  - `section`：按父块组装（`buildSectionContext`，切片规则 2），没有父块的切片按切片放入。

运行记录同时保存两份列表的配置，不修改知识库设置。

### 7.2 指标定义（按 split、题型、具体度、词面重叠分桶分别输出）

| 指标 | 定义 |
| --- | --- |
| 来源文章 Hit@1 / @5 / @10 | 文章排名前 K 中包含来源文章的题目比例 |
| 来源文章 MRR | 来源文章名次的倒数，不在排名列表中计 0 |
| Evidence Hit@topK | 回答上下文中来源文章的文本（规范化：NFKC、去空白与标点）覆盖证据原文字符二元组的比例 ≥ 0.8 即为命中，多段证据任一段命中即可；不依赖切片 ID。`metadata` 题不计算 |
| 全部证据覆盖率 | 同上，但要求每段证据都命中。合成题的多段证据不一定都是必要证据，只作参考 |
| 上下文命中率 | 回答上下文中包含来源文章任一切片的题目比例 |
| 上下文字数 | 回答上下文的平均正文字数 |
| 检索耗时 p50 / p95 | `retrieve()` 耗时，不含查询 Embedding；查询 Embedding 耗时单独统计 |
| 运行可靠性 | 降级（`warnings`）题数、调用失败题数、排名深度不足题数、因语料变化排除的题数 |
| 数据可靠性 | 生成通过率、退回 `fact` 的比例（取自数据集 `generation`） |

词面重叠分桶为 `< 0.4`、`0.4–0.6`、`≥ 0.6`。如果改进只出现在高重叠桶，说明可能只是更贴合原文措辞，需要谨慎解读。

### 7.3 失败题复判

单来源标注把「其他文章也能回答」记为失败。复判对来源文章没有排在第 1 的题目，由 AI 判断排在来源文章之前的其他文章能否回答该问题，最多判断前 10 篇；来源文章不在前 10 时判断前 10 篇。据此得到宽松指标，与严格指标并列报告：

- **宽松名次**：来源文章与复判可回答的文章中最靠前者的名次。宽松 Hit@K 即前 K 篇中有来源文章或可回答的文章；宽松 MRR 取宽松名次的倒数。来源文章排在第 10 名以后时，第 11 名起的文章不复判，宽松 MRR 略偏低，Hit@K 不受影响。
- **判定**：审核模型（业务模型 `review`）只看问题与候选文章（标题、元数据与正文），不看出题文章的参考答案与证据，给出不同但切题答案的文章也算能回答。先逐项核对问题中的对象、条件与时间范围，再给出三级结论：
  - `yes`：明确给出答案，且问题的各项限定都相符；
  - `partial`：只答了一部分，或限定条件不完全一致，或只有背景、通识；
  - `no`：不能回答。
  
  同时给出依据该文章的答案和逐字摘录的证据。只有 `yes` 且每段证据都能在文章中逐字找到（NFKC + 去空白后子串匹配）才计为可回答。
- **成本**：复判成本与失败题、排在来源文章之前的文章数成正比。结论按「题目 + 文章」缓存，各次运行与变体共用；文章正文（`content_hash`）、复判版本（`ADJUDICATION_VERSION`，修改提示或校验规则时提升）或审核模型变化后重新复判。历史运行可以随时补做。

```sh
pnpm evaluate:adjudicate <运行> [--variant=rerank,fused] [--ids=s0152,s0163] [--limit=N] [--concurrency=2] [--dry-run]
```

- `--variant` 默认取运行中的 rerank、fused；`--ids` 只复判指定题目；`--dry-run` 只统计待复判的题数、篇次与正文字数，不调用模型。
- 复判明细（分析、答案、证据、用量）追加到 `.nyz-data/eval-adjudications/<数据集>@<版本>.jsonl`，中断后重新运行即继续。
- 运行记录增加 `adjudication` 字段，包括复判版本与模型、逐题逐文章的结论、已复判的变体，以及各变体的宽松指标（同样按 split、题型、具体度、词面重叠分组）。还有文章待复判的题目计入 `unjudged`，此时宽松指标偏低。
- `evaluate:compare` 在两次运行都复判过相应变体时，另外输出宽松 Hit@K、宽松 MRR 与挽回题数。

## 八、运行与对比

### 8.1 消融配置

`--variant` 通过向 `retrieve()` 注入不同的依赖实现，融合与阈值逻辑与线上一致：

| 变体 | 注入的依赖 |
| --- | --- |
| `keyword` | 只有关键词召回 |
| `vector` | 只有子块向量召回（关键词召回返回空） |
| `summary` | 只有摘要召回 |
| `fused` | 三路召回，不 Rerank |
| `rerank` | 三路召回 + Rerank（需配置 Rerank 模型） |

同一次运行中，每道题只计算一次查询 Embedding，各变体共用，与 API 一致。检索参数取最近创建的知识库（`topK`、`similarityThreshold`、`maxContextLength`），`rerankEnabled` 由变体决定。Embedding 与 Rerank 调用失败时最多重试 2 次，避免偶发故障使 Rerank 降级为合并排序；重试后仍失败的记为降级或调用失败，单独报告。

`--context` 选择回答上下文的组装方式（第 7.1 节），`--schema=eval_<名称>` 改用 `evaluate:index` 建立的实验索引（第 8.5 节），模型配置与知识库参数也从该 schema 读取。

### 8.2 运行记录

每次运行保存到 `.nyz-data/eval-runs/<时间>-<名称>.json`，内容包括：

- 数据集名称与版本、split；
- 语料指纹与覆盖率、`parserVersions`、`chunkerVersion`；
- 知识库参数、上下文组装方式与实验 schema，以及 Embedding、Rerank 的模型与供应商（不含密钥）；
- 每题每个变体的文章排名（含各路得分）、回答上下文的切片 ID、父块 ID 与所属文章、上下文字数、耗时、警告；
- 汇总指标：每个变体的总体指标、按 split / 题型 / 具体度 / 词面重叠分组的指标、可靠性计数与耗时。

`--limit=N` 只取前 N 道题，用于冒烟测试，不作为基线。

### 8.3 对比

`evaluate:compare <运行A> <运行B>`（运行名取该名称最新的一次，也可以写运行记录的路径）输出以下内容：

- 各指标差值；
- 每题来源文章名次的升降，以及进入或跌出前 5、前 10 的题目清单；
- 证据由未命中变为命中、由命中变为未命中的题目清单（比较上下文组装方式时名次不变，看这两份清单）；
- 按题型和具体度的差值。

两次运行的数据集版本或 split 不同时拒绝对比。语料指纹不同时给出警告。只比较两边都有效的题目（未排除、未调用失败）。默认对比两次运行共有的变体；`--variant=fused:rerank` 表示 A 的 `fused` 对比 B 的 `rerank`，两个参数写同一个运行即可对比同一次运行内的两个变体。`--json` 输出完整结果。

### 8.4 基线（2026-10-24）

`baseline`：`nyz-rag-synthetic-v1` dev 238 道题，语料 1126 篇（向量化覆盖率 99.91%，标记为不完整），知识库 topK=5、阈值 0.35、上下文 6144 字，Embedding `BAAI/bge-m3`，Rerank `BAAI/bge-reranker-v2-m3`。全部变体约 4 分钟，没有降级、调用失败或因语料变化排除的题目。补齐向量化后重跑的 `baseline-full`（覆盖率 100%，不再标记为不完整）与下表的 Hit@k、证据命中完全相同，只有 vector、fused 各 1～2 道题的名次在第 5、6 名之间互换。

修复摘要召回的 HNSW 漏召回（第 8.6 节）后重跑的 `baseline-ef100` 中，keyword、vector、rerank 与 `baseline`（后面的完整表）相同，有变化的两项：

| 变体 | Hit@1 | Hit@5 | Hit@10 | MRR | 证据命中 | 上下文命中 |

查询 Embedding p50 99 ms、p95 164 ms。观察：

- **Rerank 最好**，`low` 题 Hit@1 92.5、`high` 题 95.9。分数接近上限，只看 rerank 变体难以分辨改进，切片改造的对比应同时看 `fused`、`vector` 与 `low`、词面重叠 `<0.4` 分组。

- **摘要召回**每篇只给一个切片，证据命中低（31.9）是预期的，它的作用是给相关文章加分。

### 8.5 实验索引

切片规则等需要重建索引的改动，在 `nyzrag` 库的单独 schema 中建立实验索引，业务 schema 与线上问答不受影响，基线可以随时复现：

```sh
pnpm evaluate:index --schema=eval_<名称> [--chunker=3|2] [--concurrency=4] [--reset]
```

- 新建 schema 并执行迁移，从业务 schema 复制 `model_providers`、`model_settings`、`knowledge_bases`、`data_sources`、`documents`。模型密钥按密文原样复制，不解密；nyzdata token 不复制。
- 对检索范围内的文章（ready、非重复主文档）按 `--chunker` 指定的切片规则（默认 2）在进程内重新切片并向量化，不经过队列与 Worker。
- 中断后再次运行，只处理尚未完成的文章。实验 schema 是复制时的文章快照，业务库之后的同步不会进入，需要时用 `--reset` 重建。不再使用时手动执行 `DROP SCHEMA eval_<名称> CASCADE`。
- 全量约 1126 次 Embedding 调用。模型调用准入（Redis，默认每分钟 120 次，与 API、Worker 共用）拒绝时，按返回的等待时间重试，全程约 10 分钟。期间额度被占满，线上问答的查询 Embedding 可能被拒绝而降级为关键词检索。`--concurrency=2` 即可。
- 文档级咨询锁的键名与业务库相同，业务 Worker 恰好处理同一篇时，本命令稍后重试。

### 8.6 父子块切片实验（2026-10-24）

对应[父子块建议](parent-child-chunking-recommendations.md)第二节的实验 A、B、C。

- **数据**：dev 238 道题。
- **索引**：两个实验索引都在 2026-10-24 从业务库复制，共 1126 篇。
  - `eval_legacy`：切片规则 1，6940 个切片，平均 541 字；
  - `eval_sections`：切片规则 2，5347 个父块、12428 个子块，子块平均 302 字。
- **配置**：模型与知识库参数同基线（topK=5、阈值 0.35、上下文 6144 字）。
- **运行**：

  | 运行 | 实验 | 索引 | 上下文组装 |
  | --- | --- | --- | --- |
  | `legacy-topk` | 线上配置 | `eval_legacy` | `topk` |
  | `legacy-budget` | A | `eval_legacy` | `budget` |
  | `sections-budget` | B | `eval_sections` | `budget` |
  | `sections-section` | C | `eval_sections` | `section` |

  B 与 C 的检索结果逐题相同。

rerank 变体（线上配置）：

观察：

- **基线可以复现**：`legacy-topk` 与 `baseline` 的 keyword、rerank 指标相同，vector、fused 相差不超过 0.5 个百分点，summary 的 Hit@10 相差 2.1 个百分点。
  - 差异原本归因于业务库有 1 篇文章未向量化。补齐后重跑的 `baseline-full`（覆盖率 100%，2026-10-24）与 `baseline` 各变体的 Hit@k、证据命中完全相同，与 `legacy-topk` 的差异不变，说明这个归因不成立；
  - 实际原因是摘要召回的执行计划：`summarySearchChunks` 取前 `SUMMARY_RECALL_LIMIT`（10）篇时，业务库的规划器改用 HNSW 近似索引（Index Scan + Incremental Sort），默认 `hnsw.ef_search=40`，会漏掉真正最相近的文章（如 s0159 的来源文章摘要相似度 0.745、精确排第 1，却没有被召回）；实验 schema 的统计信息不同，同一查询始终走精确扫描（摘要索引 `idx_scan` 分别为 2181 和 0）；
  - 两个 schema 的 HNSW 索引质量相当：用 dev 集 238 道题的查询向量强制走索引，`ef_search=40` 时 recall@10 分别为 98.5% 和 98.6%（漏掉来源文章 4 道、1 道），`ef_search=100` 时均为 100%。线上问答走同一函数，同样受影响。
  - 已修复（2026-10-24）：`db.ts` 的连接池在每个连接上设置 `hnsw.ef_search = 100`（会话级，事务内 `SET LOCAL` 仍可覆盖），切片向量召回同样受益。重跑的 `baseline-ef100` 中 summary 找回 4 道题（s0112、s0127、s0159、s0320 进入前 5，无题跌出），Hit@10 由 79.8 升到 81.5，fused 的 Hit@1、MRR 各升 0.4、0.2，rerank 不变；与 `legacy-topk` 剩余的差别约 1 道题，来自两边向量数值上的微小差异（同一篇文章的摘要向量余弦距离最大 7e-4，生成时的批次不同）。
- **字数预算的影响远大于切片规则**：线上 topK=5 只用了约 3000 字，是预算的一半。填满 6144 字后，fused 证据命中从 76.8 升到 94.0，rerank 从 96.8 升到 97.3。
- **B 对比 A（字数预算相同）**：
  - rerank 各项下降 0.4～0.9 个百分点（1～2 道题），在第十一节的容差内。`low` 组 Hit@10 −1.5（1 道题），词面重叠 `<0.4` 组 Hit@10 由 96.9 降为 95.3、MRR 由 94.1 降为 91.6。
  - fused 的 Hit@1 +1.7、MRR +1.0、证据命中 +2.2。
  - vector 单路明显变差，Hit@10 由 91.2 降为 87.0，MRR 由 81.0 降为 77.8。子块更小，前 20 个向量命中集中在更少的文章上，排名深度不足的题由 67 道增至 131 道。
- **C 对比 B（检索结果相同）**：
  - rerank 证据命中不变（96.8），全部证据 +0.5（1 道题）。
  - fused 证据命中 −8.1，16 道题由命中变为未命中。整个父块放入后，同样字数容纳的文章由平均 9.4 篇降为 4.9 篇（rerank 运行中统计），排名靠后的来源文章放不进上下文。可见排序准确时父块扩展没有影响，排序不准时会挤掉其他文章。
- **数据集已接近上限**：185 道证据题中，各配置的 rerank 只有 5～6 道证据未命中，其中约一半是来源文章根本不在上下文中，属于检索问题。合成题的证据大多是单段原文，父块补全上下文的作用在本数据集上无法体现。
- **耗时**：
  - rerank p50 由 604 ms 降为 520 ms，因为 Rerank 的输入切片更短；keyword、fused 的 p95 也下降了。
  - 三次 `budget`/`section` 运行的 rerank p95 都在 2600 ms 左右，其中包括与 `legacy-topk`（707 ms）同一索引的 `legacy-budget`。这是运行期间 Rerank 服务的波动，与切片规则无关。

结论：

- **父子块暂不上线**：B、C 的指标在第十一节的容差内，但没有可重复的正收益（建议文档第六节）。`CHUNKER_VERSION` 保持 1，切片规则 2、父块表与评估工具保留。
- **字数预算更值得先做**：线上只用了一半预算。调大 `topK` 或按字数预算组装上下文是检索参数调整，需要回答层评估（I）确认更长的上下文不会让回答变差。
- **如果继续父子块**：先补上下文依赖专项题（建议文档第五节），再解决子块下向量召回集中在少数文章的问题，例如加大向量召回的候选数，或按文章去重。

### 8.7 回答层评估

检索指标只说明来源文章与证据是否进入上下文，不能说明模型是否用好了它们。回答层评估对评估集逐题运行完整问答，再由审核模型评审回答：

```sh
pnpm evaluate:answer --dataset=<路径> --split=dev --name=<运行名> [--context=topk|budget|section] [--variant=fused|rerank] [--schema=eval_<名称>] [--limit=N] [--concurrency=2]
pnpm evaluate:answer --compare <运行A> <运行B> [--json]
```

- **与线上一致**：每题计算一次查询 Embedding，用 `retrieve()` 检索（`--variant` 默认按知识库：开启 Rerank 且配置了 Rerank 模型时为 `rerank`，否则为 `fused`），按 `--context` 组装上下文（第 7.1 节，同一份排名列表），用知识库回答提示词经 `buildChatMessages` 调用业务模型中的 Chat 模型。不写问答记录，也不经过 API 的限流；模型调用准入（Redis）与线上共用。
- **不降级**：线上 Chat 调用失败时退回原文摘录，评估时记为调用失败，下次运行重试，不把摘录当作回答评审。没有检索到任何切片时不调用模型，记为「无上下文」。
- **程序统计**：回答中的引用编号（`[1]`、`[1][2]`，以及 `[1, 2]`、`[1、2]`）、是否有引用、是否出现超出参考资料的编号、来源文章是否被引用。来源文章被引用的比例分两种分母：全部题目，以及来源文章在上下文中的题目（前者含检索失误，后者只看模型）。
- **LLM 评审**：审核模型（业务模型 `review`）只看到问题、参考答案与证据、送入模型的参考资料原文和回答，不知道上下文组装方式与模型配置。先写分析，再按 1～5 分打分，每项不低于 4 分计为通过：
  - `faithful`：回答的事实、数值、结论都有参考资料的依据（以参考资料为准，不是来源文章全文）；表示资料不足不算不忠实；
  - `complete`：答到参考答案的要点；用其他资料给出等价答案也算完整，与参考答案矛盾最多 2 分，表示资料不足为 1 分；
  - `citation`：引用编号指向的资料支持相应句子，关键结论都有引用；
  - 另输出是否表示资料不足（`refused`）、缺乏依据的说法与遗漏的要点。
- **局限**：参考答案只来自来源文章，其他文章给出的不同答案依赖评审判断；审核模型与 Chat 模型相同时会给出警告（同一模型评审自己的回答，得分可能偏高）。评审得分只在同一审核模型的运行之间比较。
- **工作文件**：`.nyz-data/eval-answers/<运行名>/`：
  - `run.json`：数据集、知识库参数与回答提示词、上下文组装方式、变体、实验 schema、各模型（不含密钥）；
  - `items.jsonl`：逐题追加检索结果（名次、上下文命中、证据命中、送入的切片与参考资料原文）、回答、引用统计、生成用量与耗时、评审结果；
  - `report.json`：汇总指标，按 split、题型、具体度、词面重叠分组；
  - `preview.md`：逐题预览。
- **断点续跑**：用同样的参数重新运行，只处理没有结果或调用失败的题目；评审失败的题目保留回答、只重新评审。参数、模型或评估版本（`ANSWER_EVAL_VERSION`，修改评审提示或统计规则时提升）与 `run.json` 不同时拒绝续跑，需要换用新的运行名。`--limit` 可以逐步扩大。
- **汇总指标**：上下文命中、证据命中、有引用、无效引用、来源文章被引用（两种分母）、各评审项的通过率与平均分、表示资料不足的比例、上下文字数、每题输入/输出 Token、首 Token 与生成耗时 p50/p95（从调用 Chat 模型开始计，不含检索），以及生成与评审的 Token 合计。
- **对比**：`--compare` 只比较两次运行都已评审的题目，输出两边的指标与差值、按具体度和题型的忠实/完整通过率差值，以及各评审项由通过变为未通过（或相反）、来源文章不再被引用（或开始被引用）的题目清单。数据集版本或 split 不同时拒绝对比，审核模型不同时给出警告。
- **用量**：实际用量见第 8.8 节。dev 集 238 道题按 `topk` 计，生成输入约 59 万、输出约 12 万 token，评审输入约 83 万、输出约 7 万 token；`budget` 的输入约翻倍。

### 8.9 失败题复判结果（2026-10-24）

- **范围**：对 `baseline-chunker3` 的 rerank、fused 变体复判。来源文章没有排在第 1 的共 56 道题、203 篇次，s0152、s0163 另外复判了全部五个变体（54 篇次）。
- **用量**：审核模型 gpt-6.1-sol，共 228 篇次，输入约 72 万、输出约 6 万 token，并发 3。
- **结论分布**：yes 17、partial 53、no 158；17 个 yes 的证据全部通过校验。
- **证据校验规则**：最初要求每段证据逐字出现，s0041 的两个 yes 因此被拒。模型摘录时有跨行拼接、补上解析时去掉的列表编号等情况，有的证据段与原文不完全一致。校验因此改为与证据命中相同的规则（第 7.3 节），只重算已有结论，没有重新调用模型。

| fused | 76.9 → 80.3 | 92.9 → 93.7 | 98.7 → 99.2 | 84.0 → 86.2 | 12 道 |

- fused：`low` 的 Hit@1 由 64.2 升到 67.2，`high` 由 81.9 升到 85.4。

keyword、vector、summary 只在与 rerank、fused 重叠的文章上有结论，还有 9～83 道题待复判，宽松指标偏低，未列出。

两道优先复判的题：

- **s0152 是真正的检索失败**。五个变体排名中的 26 篇其他文章都不能回答。两篇判为 partial：一篇讲预锂化添加剂的保护层，一篇讲负极覆盖涂层抗剥离，都不是「金属箔裁切边缘的局部覆膜」。来源文章只在 vector 变体中排第 12。
- **s0163 是题目过泛**。问题没有限定材料、处理方法与循环条件，3 篇其他文章给出了「处理与未处理样品的容量保持率对比」（如钛富集表面处理 77.4% 对 66.2%），判为 yes。rerank 的宽松名次为 3，fused 为 7，summary 为 2，vector 为 10。另有 13 篇只给出处理样品的保持率、没有对照，判为 partial。

挽回的题分为两类：

- **同一研究的另一篇文章**（14 道中的 9 道）：
  - s0077、s0085、s0168 的可回答文章与来源文章标题完全相同；
  - s0020、s0108、s0171、s0319 是同一论文的不同解读或转载；
  - s0032 是同系列报告（BAT608 与 BAT610）；
  - s0041 是同一企业的系列专利解读。
  
  正文指纹去重只识别正文完全相同的文章。业务库 1126 篇主文档中有 14 组、28 篇标题完全相同，标题不同的同源文章更多。单来源标注把它们记为失败，严格指标因此偏低。
- **其他文章确实能回答**（5 道）：s0022（同一时段的另一篇电解液周报）、s0053、s0132（不同研究给出了相应的设计或结构）、s0163（题目过泛）、s0277（同一企业的另一篇报道）。

结论：

- **严格指标低估了检索效果**。rerank 不在第 1 的 12 道题中，9 道有排在来源文章之前、同样能回答的文章：8 道的宽松名次为 1，s0163 为 3。真正的排序失误只剩 s0152（未召回）以及 s0231、s0245（来源文章分别排第 2、4），都是 `low` 题。
- **剩下 3 道失败题的原因（rerank）**：都不是代码缺陷，是模型没能把 `low` 题的通用说法对应到原文术语：
  - s0152：问题说「金属箔裁切边缘」「局部覆盖膜」，专利原文是「集电体端面」「保护层」，关键词召回不到，向量召回排第 15 个切片。RRF 合并后只保留前 30 个候选（`CANDIDATE_LIMIT`），只有一路召回、名次靠后的切片被截掉，没有进入 Rerank。直接把来源切片送入 Rerank 也只得 0.19（第 1 名 0.79），放宽候选数救不回来；dev 集中被截断丢掉来源文章的也只有这一道。
  - s0245：问题说「高电流 / 低电流化成」，原文写「1C / C/20」。关键词召回排第 1，向量与摘要召回都没召回，Rerank 只给 0.19（第 1 名 0.56）。曾怀疑是 Rerank 截断了切片末尾，实测证据段在 759 字正文的第 234 字处；只保留证据段或把它移到开头，得分也只升到 0.26～0.28，不是截断问题。来源文章排第 4，但它的切片排在第 5 个之后，topK=5 时进不了上下文，回答层评估中回答表示资料不足。
  - s0231：Rerank 打分接近平局（0.9646 对 0.9626），第 1 名是另一篇讲硅负极 D50 粒径的专利（复判为不能回答）。来源文章排第 2，仍在上下文中，回答层三项都是 5 分，影响可忽略。
  
  可能的改进是问题改写（如先生成假设答案或术语化改写，再检索），或换用更强的 Rerank 模型，都需要用本评估集验证后再决定。
- **对比改动时仍以严格指标为主**。宽松指标随复判结论变化，只用来区分「排序失误」与「其他文章也能回答」。改动后跌出前 1、前 10 的题目，先查看复判结论再下结论。
- **新运行的复判成本低**：结论按「题目 + 文章」复用，新运行只需复判新出现在来源文章之前的文章。

## 十、使用流程

```sh
# 1. 试点：抽样并生成 50 篇，检查通过率、失败原因、词面重叠与用量
pnpm --filter @nyz-rag/processing evaluate:generate --name=nyz-rag-synthetic-v1 --limit=50

# 2. 调整提示后生成全部样本（断点续跑），并冻结
pnpm --filter @nyz-rag/processing evaluate:generate --name=nyz-rag-synthetic-v1
pnpm --filter @nyz-rag/processing evaluate:generate --name=nyz-rag-synthetic-v1 --freeze

# 3. 记录基线（--variant 默认为全部五个变体；相对路径按执行命令的目录解析）
pnpm evaluate:retrieval --mode=hybrid --dataset=packages/processing/test/evaluation/nyz-rag-synthetic-v1.json --split=dev --name=baseline

# 4. 修改检索参数后再运行，并与基线对比
pnpm evaluate:retrieval --mode=hybrid --dataset=packages/processing/test/evaluation/nyz-rag-synthetic-v1.json --split=dev --variant=fused,rerank --name=<运行名>
pnpm evaluate:compare baseline <运行名>
pnpm evaluate:compare baseline baseline --variant=fused:rerank   # 同一次运行内对比两个变体

# 5. 切片规则的改动：建立实验索引后在其上运行（第 8.5、8.6 节）
pnpm evaluate:index --schema=eval_legacy --chunker=1 --concurrency=2
pnpm evaluate:index --schema=eval_sections --chunker=2 --concurrency=2
pnpm evaluate:retrieval --mode=hybrid --dataset=packages/processing/test/evaluation/nyz-rag-synthetic-v1.json --split=dev --schema=eval_legacy --context=budget --name=legacy-budget
pnpm evaluate:retrieval --mode=hybrid --dataset=packages/processing/test/evaluation/nyz-rag-synthetic-v1.json --split=dev --schema=eval_sections --context=section --name=sections-section
pnpm evaluate:compare legacy-budget sections-section

# 6. 回答层评估（调用 Chat 与审核模型，产生费用；第 8.7 节）：比较线上 topK 与按字数预算组装
pnpm evaluate:answer --dataset=packages/processing/test/evaluation/nyz-rag-synthetic-v1.json --split=dev --name=answer-topk
pnpm evaluate:answer --dataset=packages/processing/test/evaluation/nyz-rag-synthetic-v1.json --split=dev --context=budget --name=answer-budget
pnpm evaluate:answer --compare answer-topk answer-budget

# 7. 失败题复判（调用审核模型，产生费用；第 7.3 节）：先统计，再复判，宽松指标写入运行记录
pnpm evaluate:adjudicate baseline-chunker3 --dry-run
pnpm evaluate:adjudicate baseline-chunker3
```

根目录的 `evaluate:*` 脚本转发到 `@nyz-rag/processing`。dev 集 238 道题、全部变体按顺序运行约需数分钟，`--concurrency` 可以并行，但会使耗时指标偏高。

## 十一、验收规则

检索或切片的改动合入前，在 dev 集上对比基线，满足以下条件：

- 来源文章 Hit@10、MRR 下降不超过 1 个百分点，Evidence Hit@topK 不下降（同为 1 个百分点容差）；
- 任一题型或具体度分组的 Hit@10 下降不超过 3 个百分点，超过时在说明中给出原因，并列出跌出前 10 的题目；
- 检索耗时 p95 增加不超过 30%，超过时说明原因；
- 说明中注明改进集中在哪个词面重叠分桶。

每完成一个阶段（例如切片改造上线前），在 test 集上运行一次，并记录到 `docs/module-status.md`。记录时注明「合成基线，单来源标注」。

## 十二、后续：真实问题集

有人力或有真实提问积累后再实施，目前不做：

- **真实问题银标（无需人工标注）**：从 `chat_messages` 导出问题（差评优先，按问题去重），由 AI 去除个人信息并补全指代；用多种检索配置各取前 10 篇合并为候选池，由 AI 按 0～3 分级判定相关度并摘取证据；开发者抽查约 10%。标记为 `source=real-silver`，单独报告，此时可以计算 Recall、nDCG 和上下文精度。未复核的导出文件只放在 `.nyz-data/evaluation/`。
- **人工标注集**：业务人员盲写问题、双人标注与裁决（加权 Cohen's κ ≥ 0.6），需要 `eval_questions` / `eval_judgments` 表和管理端标注界面，人力到位后再设计。
