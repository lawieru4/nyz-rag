# 检索评估集方案：文章派生合成基线

状态：生成（G）、评估（A）与对比（B）已实现，`nyz-rag-synthetic-v1` 已冻结（第 5.5 节），dev 集基线已运行（第 8.4 节）。目标是在没有人工标注资源的条件下，由 AI 按文章生成带原文证据的问题，建立可重复运行的检索回归基线，作为切片、检索、Rerank 等调整的对比依据。[切片改造](chunking-design.md)以本基线验收。

## 一、定位与边界

- **这是合成题，不是真实问题**：问题由 AI 根据单篇文章生成，参考答案与证据来自原文，经程序校验和 AI 审核，没有人工标注。数据集标记 `source=synthetic`，指标单独报告，不与将来的真实问题集合并，不用于宣称生产问答质量或用户满意度。
- **单来源标注**：每道题只确定「生成它的来源文章」和「原文证据」两项。其他文章也可能回答同一问题，但首版不判定，因此不报告完整 Recall、nDCG 和上下文精度，只报告与来源文章相关的指标（第七节）。
- **用途**：比较同一语料上不同切片、Embedding、检索路径、融合与 Rerank 配置的相对变化。合成题系统性偏向「问题措辞接近原文」，绝对数值偏乐观，以两次运行的差值和逐题名次变化为主要依据。
- **评估真实链路**：直接调用问答使用的 `retrieve()`（关键词 + 子块向量 + 摘要召回、RRF、Rerank），并能逐路消融。
- **标注不随切片变化**：生成题目时使用完整正文，不参考当前切片；标注到「文章 + 证据原文」，不记录切片 ID。切片方案改变后数据集仍然有效。
- **检索只输入问题**：参考答案与证据只用于校验题目质量和计算证据命中，检索时不得带入。
- **防止过拟合**：按文章固定划分 dev / test，调参只看 dev，test 只在阶段验收时运行。

## 二、前置条件

1. **全量语料入库**：在管理后台配置 nyzdata token 并完成全量同步，在模型配置中选择 Embedding 模型并完成向量化。以数据库中的实际文章数为准，不沿用估算的「约 7068 篇」。
2. **评估语料范围**：文章接口来源、`status = ready`、非重复（`duplicate_of IS NULL`，处理状态不是 `duplicate`）的主文档。向量化未完成的文章计入覆盖率报告；覆盖率不足 100% 时，hybrid 模式的运行结果标记为不完整。
3. **生成与审核模型可用**：生成使用业务模型中的 Chat 模型，审核使用业务模型中的「审核」模型（`review`，温度建议为 0）。审核模型建议与 Chat 选用不同的模型，避免同一模型审核自己生成的题目；未配置审核模型时命令报错，不退回 Chat 模型。
4. **评估用知识库参数固定**：`topK`、`similarityThreshold`、`rerankEnabled`、`maxContextLength` 写入每次运行记录。比较两次运行时只改变待验证的变量。

## 三、语料快照与抽样

### 3.1 语料快照

生成开始时冻结语料快照，写入数据集的 `corpus` 字段：

| 字段 | 内容 |
| --- | --- |
| `documents` | 符合第二节范围的文章数 |
| `fingerprint` | 按 `articleKey` 排序的 `articleKey:content_hash` 列表的 SHA-256。切片或向量变化不影响它，正文变化才会改变 |
| `parserVersions` | `parser_version` 的分布 |
| `chunkerVersion` | 切片规则版本（`CHUNKER_VERSION` 引入前为空） |
| `embeddingModel` / `embeddingCoverage` | 默认 Embedding 模型与已向量化文章的比例 |

评估运行时重新计算指纹。与数据集不一致时给出警告，并逐题检查：来源文章已不在语料中，或证据已不在原文（`metadata` 题含标题与元数据线索）中的题目列出并排除在指标之外。冻结的数据集不保存逐篇的 `content_hash`，因此以证据是否仍在原文中判断，正文改动未涉及证据的题目仍然有效。

### 3.2 抽样

不做一篇一题的全量覆盖。原因是每次运行的查询 Embedding、Rerank 调用和耗时都与题数成正比，消融和反复对比时成本会成倍增加。300～400 道题时 Hit@10 的标准误约 2～3 个百分点；同一批题目在两次运行间做逐题配对对比，比单独看两个绝对值更灵敏，足以分辨改动效果。

- **样本量**：首版抽 400 篇，按约 85% 的通过率预计得到约 340 道题；语料增长后按版本扩充到约 600 篇。
- **排除**：正文不足 300 字的文章（以图片为主，没有可出题的文字）。
- **分层**：按栏目（`category`，样本不足 20 篇的栏目合并为「其他」）、科研栏目内标题是否识别出期刊（`metadata.titleMeta.journal`），以及正文长度三分位分层，按比例抽样。不按发布年份分层，因为现有语料 97% 发布于 2026 年。

2026-10-23 的业务库语料情况：

- **文章数**：主文档 1126 篇，其中 1125 篇已向量化，使用 `BAAI/bge-m3`、1024 维；共 6940 个切片。
- **栏目分布**：科研 597 篇（其中 503 篇识别出期刊），能学堂 271、供应链 67、能人堂 59、排行榜 43、储能系统 43，其余栏目合计不足 50 篇。
- **正文长度**：中位 3390 字，P90 5115 字，最长 2.8 万字；不足 300 字的 4 篇。
- **元数据**：有关键词的 803 篇，标题识别出机构的 388 篇，有项目负责人的只有 37 篇。

**语料增长**：同步仍在进行时，已有题目在文章不变的情况下依然有效，但语料指纹会变，基线运行需要在新语料上重跑；不需要重新生成题目。文章越多，干扰项越多，指标会自然下降，不同语料快照上的运行不能直接比较（`evaluate:compare` 会给出警告）。
- **可复现**：抽样使用固定随机种子，种子与分层规则写入数据集的 `sample` 字段。

### 3.3 划分

按 `articleKey` 的 SHA-256 取模确定 `split`：dev 约 2/3，test 约 1/3。同一篇文章的题目始终落在同一侧。以后扩充时，已有文章的划分不变。

## 四、题目生成

### 4.1 输入

每篇文章调用一次生成，输入为标题、完整清洗正文（`documents.content`，正文中位约 4000 字、最长约 2.1 万字，无需截断）、元数据（关键词、项目名称、负责人、承担单位、标题识别出的期刊与机构），以及预先分配的题型与具体度。

### 4.2 题型与具体度

抽样后为每篇文章预先分配目标题型与具体度，以控制整体分布。不满足条件的文章，生成器可以退回 `fact`，退回会被记录。

| 类型 `type` | 目标占比 | 说明 | 分配条件 |
| --- | --- | --- | --- |
| `fact` | 40% | 单篇事实：数值、结论、方法 | 任意文章 |
| `mechanism` | 25% | 机制、原因、作用 | 正文含机制或原因论述 |
| `metadata` | 20% | 以机构、期刊、负责人、项目为线索找文章 | 有对应元数据 |
| `term` | 15% | 化学式、材料名、术语的精确匹配 | 正文含化学式或专有术语 |

| 具体度 `specificity` | 目标占比 | 要求 |
| --- | --- | --- |
| `high` | 约 68% | 可以使用原文的专有名词，但不得照抄句子；元数据题与术语题依赖原文专有名词，固定为 high |
| `low` | 约 32% | 用描述性或上位说法提问，不出现原文中的材料名、化学式、数值、机构名和人名，模拟不熟悉原文措辞的用户；事实题与机制题各一半为 low |

`low` 题天然可能被多篇文章回答，单来源 Hit 会偏低，所以必须与 `high` 题分开报告（第七节）。

首版不生成 `compare`（需跨篇标注）、`followup`（合成的多轮追问不像真实用户），也不生成 `unanswerable`（无法证明语料中确实没有答案）。

### 4.3 生成要求

输出 JSON：`question`、`answer`、`evidence[]`（1～3 段原文，每段不超过 200 字）、`type`、`specificity`。提示中写明以下要求：

- 问题能独立理解：不出现「本文」「该研究」「上述」「作者」等指代；
- 问题不照抄标题或证据句，不把答案写进问题；
- 问题指向这篇文章特有的内容（这项研究、产品、专利、报告或人物的具体数据、方法与结论），不问教科书通识或多数文章都会提到的常识，也不问「这篇文章讲了什么」；
- 不在问题中使用专利号、DOI、文章编号等用户通常不知道的标识符；
- 价格、行情、周报月报、装机或销量、排行榜、政策动态等时效性内容，问题必须写明时间范围，优先取自标题或正文，没有时按发布日期写（提示的文章头含发布日期）。否则同系列其他时期的文章也能回答；
- `low` 题用领域通用说法，自然直白，不写成刻意回避名称的谜语式描述；时间范围不算具体数值。人物或企业介绍类文章，问不依赖姓名也能自然表述的内容，不用身份描述代替姓名去问个人经历；
- 问题像真实业务人员会问的问题，长度 10～60 字；
- 证据必须逐字摘自正文（`metadata` 题可摘自元数据字段），答案只能依据证据，不得补充原文没有的内容。

## 五、校验与审核

### 5.1 程序校验

| 检查 | 规则 |
| --- | --- |
| 结构 | 字段齐全，类型与具体度合法，长度在范围内 |
| 证据存在 | 规范化（NFKC、去空白）后，每段证据都是正文的子串；`metadata` 题也可以是元数据字段的子串 |
| 指代与泄漏 | 不含禁用指代词；答案中的关键数值或短语不出现在问题里（年份除外，它是时效性问题应写明的时间范围） |
| 词面重叠 | 用 `searchTerms` 计算问题词项与「证据 + 标题」词项的重叠率，写入 `lexicalOverlap`。`low` 题超过 0.5、`high` 题超过 0.8 时打回（初始阈值，试点后调整） |
| 重复 | 与已通过题目的问题词项 Jaccard ≥ 0.6 时打回 |

### 5.2 AI 审核

使用审核模型独立调用一次，输入完整正文、问题、答案和证据。审核员先写一段 `analysis`，分析同系列或同主题的其他文章（其他时期的周报、同一材料的其他研究、同一企业的其他报道）能否同样回答、是否属于通识，再逐项打 1～5 分并说明理由：

- `standalone`：不看文章也能理解问题在问什么（时效性内容缺少时间范围也算不能独立理解）；
- `supported`：证据足以支持答案；
- `faithful`：答案没有编造或过度推断；
- `specific`：问题有明确答案，不是开放式讨论；
- `distinctive`：问题指向这篇文章特有的内容，不是多数同类文章都能回答的通识。单来源标注只认来源文章，通识题会把其他能回答的文章判为错误；
- `natural`：措辞像真实提问，不是对原文的改写，不是谜语式描述，不含用户通常不知道的标识符。

每项都不低于 4 分（`REVIEW_PASS_SCORE`）才算通过，分数缺失或不合法视为不通过。前两版用布尔判断，审核几乎不拒题，第 3 版改为先分析再打分。`report.json` 记录已通过题目的各项平均分，预览中附每题得分与分析，用于观察审核口径。

### 5.3 重试与状态

每篇文章的状态依次为 `pending` → `generated` → `checked` → `approved`，或最终为 `rejected`。程序校验或审核未通过时，把失败原因反馈给生成器重试，最多 3 次。仍未通过的标记 `rejected` 并保留原因，不为凑数收入坏题。

工作文件放在 `.nyz-data/evaluation/<数据集名>/`（gitignored）：

- `sample.json`：语料快照、抽样结果，以及每篇文章的目标题型、具体度和正文指纹；
- `items.jsonl`：每篇文章每次尝试的生成、校验、审核结果和 token 用量，只追加不修改；
- `report.json`：本次范围内的通过率、失败原因、词面重叠分布和用量；
- `preview.md`：逐题预览，供人工浏览。

命令中断后从未完成的文章继续，已有结果不重复调用模型。模型调用失败（网络错误、供应商过载、审核输出无法解析）先退避重试 2 次，仍失败则记为 `error`，不计入尝试次数，下次运行重新处理。样本文章的正文在抽样后发生变化或被删除时，该文章记为 `stale` 并跳过。

### 5.4 试点

先抽 50 篇试生成，检查以下各项：

- 通过率与失败原因分布；
- 词面重叠分布；
- 重复率；
- 模型调用量与 token 用量；
- 开发者浏览约 20 道题，凭直觉判断是否像真实提问。

据此调整提示和阈值，提示版本号（`SYNTHETIC_PROMPT_VERSION`）随之提升。提升后，旧版本的记录保留在 `items.jsonl` 中但不再计入，样本文章用新提示重新生成，因此冻结的数据集只包含同一版本提示生成的题目。之后再扩展到全部样本。

第 1 版试点（2026-10-23，50 篇）的结果：

- 生成：通过 48 篇、拒绝 1 篇，通过的题平均尝试 1.3 次；失败原因主要是词面重叠过高。
- 审核：49 次审核只拒绝了 1 次，明显偏宽。
- 问题：浏览后发现三类问题审核都没有拦下——通识题（如 LiC₆ 的理论容量）、为避开原文用词写成谜语的 low 题、问题中出现专利号。
- 调整：第 2 版提示补充了上述要求，审核新增 `distinctive` 一项。
- 稳定性：审核供应商约 18% 的调用在流中返回过载错误，记为 `error` 后补跑即可完成。

第 2 版试点（同一批 50 篇）的结果：

- 生成：通过 48 篇、拒绝 2 篇，通过的题平均尝试 1.2 次。
- 词面重叠：低于 0.4 的 18 题、0.4～0.6 的 20 题、不低于 0.6 的 10 题。
- 用量：生成输入约 16 万、输出约 9 万 token；审核输入约 15 万、输出约 0.5 万 token。
- 改善：专利号和教科书通识题已消失，谜语式的 low 题减少。
- 遗留问题：
  - 审核仍然一题未拒，过滤主要靠生成提示和程序校验；
  - 行情周报类问题没有写明时间范围（如「DTD 的价格运行态势」），同系列的其他周报也能回答；
  - 人物介绍类 low 题仍有谜语式写法。

第 3 版（审核改为先分析再打分，时效性内容须写明时间范围，人物介绍类 low 题不用身份描述代替姓名；审核模型换为 gpt-6-luna）试点结果：

- 生成：通过 46 篇、拒绝 4 篇，通过的题平均尝试 1.4 次。
- 审核：拒绝 13 次，其中 12 次因为 `distinctive` 低于 4 分（通识题、同主题文章也能回答），审核开始起作用。
- 遗留问题：标题和正文都没有日期的周报（如「“金九”临近，电解液原料涨势再扩大」）仍然生成了不带时间的报价题，审核也放行了。

第 4 版（提示的文章头加入发布日期，没有其他时间时按发布日期写时间范围）试点结果：

- 生成：通过 46 篇、拒绝 4 篇，通过的题平均尝试 1.35 次。
- 审核：拒绝 10 次，其中 9 次因为 `distinctive`；已通过题目的平均分 `distinctive` 4.67，`natural` 4.8，其余各项接近 5。
- 时效性：行情类问题都写明了时间（如「2026年8月下旬，六氟磷酸锂的报价维持在什么区间？」）。
- 词面重叠：低于 0.4 的 14 题、0.4～0.6 的 21 题、不低于 0.6 的 11 题。
- 用量：生成输入约 19 万、输出约 11 万 token；审核输入约 19 万、输出约 2 万 token（审核需要先写分析，输出比第 2 版多）。
- 遗留问题：
  - `low` 题更容易被拒：被拒的 4 篇中 3 篇是 `low`，通过的题中 `low` 只占 22%，低于目标的约 32%。冻结前按具体度分别报告，不混算。
  - 带日期的 `low` 题，日期本身会与标题重叠，词面重叠更容易超限（如磷酸铁锂周报一题）。

第 4 版换审核模型重跑（审核改为 gpt-6.1-sol，旧记录存档后同一批 50 篇重新生成）：

- 生成：通过 42 篇、拒绝 8 篇，通过的题平均尝试 1.5 次；审核拒绝 24 次，其中 20 次因为 `distinctive`，比 gpt-6-luna 更严。
- 具体度：被拒的 8 篇全部是 `low`，通过的题中 `low` 只有 6 道（14%），`mechanism/low` 为 0。`low` 要求不出现文章特有的名称和数值，问题越泛化，同主题的其他文章越可能也能回答，与单来源标注要求的 `distinctive` 天然冲突。
- 用量：生成输入约 24 万、输出约 12 万 token；审核输入约 22 万、输出约 3 万 token。

决定不再调整提示，按第 4 版直接生成全量，`low` 题按具体度分开统计、只作参考。

### 5.5 全量生成（第 4 版，2026-10-23）

400 篇（含试点 50 篇）用 deepseek-flash 生成、gpt-6.1-sol 审核，并发 3，约 2 小时：

- 结果：通过 350 篇、拒绝 50 篇（87.5%），通过的题平均尝试 1.38 次；1 篇 `term` 回退为 `fact`。调用失败 13 次（供应商在流中报错），重新运行后全部补齐。
- 按目标：`term/high` 57/60、`fact/high` 71/72、`metadata/high` 73/80、`mechanism/high` 50/58、`fact/low` 70/88、`mechanism/low` 29/42。通过的题中 `low` 99 道（28%），比试点的 14% 高，试点 50 篇的比例偏差较大。
- 按栏目：科研 199/212、能学堂 80/97、供应链 20/23、储能系统 14/16、其他 14/16、排行榜 11/15、能人堂 12/21。能人堂（人物专访）通过率最低，`low` 题难以在不点名的情况下只指向一篇文章。
- 词面重叠：<0.4 有 97 道、0.4～0.6 有 170 道、≥0.6 有 83 道。
- 失败原因（按尝试计）：审核未通过 132 次（127 次因为 `distinctive`）、词面重叠过高 62 次、问题长度 50 次、证据不在原文中 15 次、格式错误 13 次。
- 通过的题审核平均分：`distinctive` 4.78、`natural` 4.85，其余均在 4.9 以上。
- 用量：生成输入约 170 万、输出约 94 万 token；审核输入约 159 万、输出约 18 万 token。
- 被拒的 50 篇不进入数据集（见 5.3），能人堂、能学堂的题数因此比抽样比例略少。
- 冻结为 `packages/processing/test/evaluation/nyz-rag-synthetic-v1.json`：350 道题，dev 238 道（`low` 67）、test 112 道（`low` 32）。

- `labels` 合成题只有来源文章一项，`relevance` 固定为 3。字段结构保留多文章和 0～3 分级，供以后的真实问题集或复判结果使用。
- `history` / `filters` / `answerable` 合成题分别固定为空数组、`null`、`true`，为以后的真实问题保留。
- 校验规则：
  - ID 唯一，问题非空；
  - `articleKey` 存在于语料；
  - 证据可在正文（或 `metadata` 题的元数据）中找到；
  - `source=synthetic` 时 `provenance` 必须声明合成且未经人工验证。
- 兼容读取：现有 `packages/processing/test/evaluation/retrieval-dataset.json`（schemaVersion 1）读取时转为 v2，`source=synthetic`，题型记为 `fact`、划分记为 `dev`，原分类保存在 `notes`，证据转为数组；可回答性规则只用于 v2。它保留为 200 篇样本上的冒烟测试。
- 冻结版本提交到 `packages/processing/test/evaluation/<名称>.json`（首版为 `nyz-rag-synthetic-v1.json`），冻结后不再修改；修正或扩充时发布新版本。

## 七、指标

### 7.1 排名列表与回答上下文

线上 `retrieve()` 只返回 `topK`（默认 5）个切片，不能直接当作前 10 篇文章的排名。评估时区分两份列表：

- **排名列表**：以 `topK = 30`（合并后的候选上限）调用 `retrieve()`。开启 Rerank 时，Rerank 的 `topN` 也随之为 30；Rerank 对每个切片独立打分，前 5 名与 `topN = 5` 时相同。切片按名次依次取所属文章、去重，得到文章排名。候选不足 10 篇文章的题目计入「排名深度不足」并单独报告。
- **回答上下文**：取排名列表前 `知识库 topK` 个切片，经 `buildAnswerContext(…, maxContextLength)` 截取，与线上进入模型的内容一致。

运行记录同时保存两份列表的配置，不修改知识库设置。

### 7.2 指标定义（按 split、题型、具体度、词面重叠分桶分别输出）

| 指标 | 定义 |
| --- | --- |
| 来源文章 Hit@1 / @5 / @10 | 文章排名前 K 中包含来源文章的题目比例 |
| 来源文章 MRR | 来源文章名次的倒数，不在排名列表中计 0 |
| Evidence Hit@topK | 回答上下文中来源文章的切片文本（规范化：NFKC、去空白与标点）覆盖证据原文字符二元组的比例 ≥ 0.8 即为命中，多段证据任一段命中即可；不依赖切片 ID。`metadata` 题不计算 |
| 上下文命中率 | 回答上下文中包含来源文章任一切片的题目比例 |
| 检索耗时 p50 / p95 | `retrieve()` 耗时，不含查询 Embedding；查询 Embedding 耗时单独统计 |
| 运行可靠性 | 降级（`warnings`）题数、调用失败题数、排名深度不足题数、因语料变化排除的题数 |
| 数据可靠性 | 生成通过率、退回 `fact` 的比例（取自数据集 `generation`） |

词面重叠分桶为 `< 0.4`、`0.4–0.6`、`≥ 0.6`。如果改进只出现在高重叠桶，说明可能只是更贴合原文措辞，需要谨慎解读。

### 7.3 失败题复判（第二阶段）

对来源文章没有进入前 10 的题目，只让 AI 判断排在来源文章之前（或前 10 中）的其他文章能否回答该问题，结果写入运行记录。据此得到「宽松 Hit@K」：前 K 中有来源文章或复判可回答的文章即为命中。宽松 Hit 与严格 Hit 并列报告。复判成本只与失败题数量成正比。首版运行先保存逐题完整排名，复判以后可以对历史运行补做。

## 八、运行与对比

### 8.1 消融配置

`--variant` 通过向 `retrieve()` 注入不同的依赖实现，融合与阈值逻辑与线上一致：

| 变体 | 注入的依赖 |
| --- | --- |
| `keyword` | 只有关键词召回 |
| `vector` | 只有子块向量召回（关键词召回返回空） |
| `summary` | 只有摘要召回 |
| `fused` | 三路召回，不 Rerank |
| `rerank` | 三路召回 + Rerank（需配置 Rerank 模型） |

同一次运行中，每道题只计算一次查询 Embedding，各变体共用，与 API 一致。检索参数取最近创建的知识库（`topK`、`similarityThreshold`、`maxContextLength`），`rerankEnabled` 由变体决定。Embedding 与 Rerank 调用失败时最多重试 2 次，避免偶发故障使 Rerank 降级为合并排序；重试后仍失败的记为降级或调用失败，单独报告。

### 8.2 运行记录

每次运行保存到 `.nyz-data/eval-runs/<时间>-<名称>.json`，内容包括：

- 数据集名称与版本、split；
- 语料指纹与覆盖率、`parserVersions`、`chunkerVersion`；
- 知识库参数，以及 Embedding、Rerank 的模型与供应商（不含密钥）；
- 每题每个变体的文章排名（含各路得分）、回答上下文的切片 ID 与所属文章、耗时、警告；
- 汇总指标：每个变体的总体指标、按 split / 题型 / 具体度 / 词面重叠分组的指标、可靠性计数与耗时。

`--limit=N` 只取前 N 道题，用于冒烟测试，不作为基线。

### 8.3 对比

`evaluate:compare <运行A> <运行B>`（运行名取该名称最新的一次，也可以写运行记录的路径）输出以下内容：

- 各指标差值；
- 每题来源文章名次的升降，以及进入或跌出前 5、前 10 的题目清单；
- 按题型和具体度的差值。

两次运行的数据集版本或 split 不同时拒绝对比。语料指纹不同时给出警告。只比较两边都有效的题目（未排除、未调用失败）。默认对比两次运行共有的变体；`--variant=fused:rerank` 表示 A 的 `fused` 对比 B 的 `rerank`，两个参数写同一个运行即可对比同一次运行内的两个变体。`--json` 输出完整结果。

### 8.4 基线（2026-10-24）

`baseline`：`nyz-rag-synthetic-v1` dev 238 道题，语料 1126 篇（向量化覆盖率 99.91%，标记为不完整），知识库 topK=5、阈值 0.35、上下文 6144 字，Embedding `BAAI/bge-m3`，Rerank `BAAI/bge-reranker-v2-m3`。全部变体约 4 分钟，没有降级、调用失败或因语料变化排除的题目。

| 变体 | Hit@1 | Hit@5 | Hit@10 | MRR | 证据命中 | 上下文命中 | 检索 p50 / p95 | 排名深度不足 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| keyword | 91.6 | 96.2 | 97.5 | 93.8 | 89.7 | 96.2 | 126 / 182 ms | 26 |
| vector | 75.6 | 88.2 | 91.2 | 81.0 | 70.3 | 85.3 | 75 / 91 ms | 69 |
| summary | 62.6 | 74.4 | 79.8 | 68.0 | 31.9 | 74.4 | 8 / 13 ms | 0 |
| fused | 76.9 | 92.4 | 98.7 | 84.0 | 76.8 | 92.0 | 131 / 185 ms | 0 |
| rerank | 95.0 | 99.2 | 99.2 | 97.0 | 96.8 | 98.7 | 613 / 710 ms | 0 |

查询 Embedding p50 99 ms、p95 164 ms。观察：

- **Rerank 最好**，`low` 题 Hit@1 92.5、`high` 题 95.9。分数接近上限，只看 rerank 变体难以分辨改进，切片改造的对比应同时看 `fused`、`vector` 与 `low`、词面重叠 `<0.4` 分组。
- **关键词单路的 Hit@1 高于 fused**（91.6 对 76.9）：RRF 把向量与摘要召回的其他文章排到了前面，但 fused 的 Hit@10 最高（98.7），为 Rerank 提供了最完整的候选。合成题偏向原文措辞，关键词的优势在真实问题上可能偏高。
- **向量单路**有 69 道题排名不足 10 篇文章，原因是相似度阈值 0.35 过滤了候选。
- **摘要召回**每篇只给一个切片，证据命中低（31.9）是预期的，它的作用是给相关文章加分。
- Rerank 没有排在第 1 的 12 道题中，2 道（s0152、s0163）任何变体的排名列表里都没有来源文章，都是问题较泛的 `low` 题，可能也能由其他文章回答（第 5.4 节）。

## 十、使用流程

```sh
# 1. 试点：抽样并生成 50 篇，检查通过率、失败原因、词面重叠与用量
pnpm --filter @nyz-rag/processing evaluate:generate --name=nyz-rag-synthetic-v1 --limit=50

# 2. 调整提示后生成全部样本（断点续跑），并冻结
pnpm --filter @nyz-rag/processing evaluate:generate --name=nyz-rag-synthetic-v1
pnpm --filter @nyz-rag/processing evaluate:generate --name=nyz-rag-synthetic-v1 --freeze

# 3. 记录基线（--variant 默认为全部五个变体；相对路径按执行命令的目录解析）
pnpm evaluate:retrieval --mode=hybrid --dataset=packages/processing/test/evaluation/nyz-rag-synthetic-v1.json --split=dev --name=baseline

# 4. 修改检索或切片后再运行，并与基线对比
pnpm evaluate:retrieval --mode=hybrid --dataset=packages/processing/test/evaluation/nyz-rag-synthetic-v1.json --split=dev --variant=fused,rerank --name=parent-child
pnpm evaluate:compare baseline parent-child
pnpm evaluate:compare baseline baseline --variant=fused:rerank   # 同一次运行内对比两个变体
```

根目录的 `evaluate:*` 脚本转发到 `@nyz-rag/processing`。dev 集 238 道题、全部变体按顺序运行约需数分钟，`--concurrency` 可以并行，但会使耗时指标偏高。

## 十一、验收规则

检索或切片的改动合入前，在 dev 集上对比基线，满足以下条件：

- 来源文章 Hit@10、MRR 下降不超过 1 个百分点，Evidence Hit@topK 不下降（同为 1 个百分点容差）；
- 任一题型或具体度分组的 Hit@10 下降不超过 3 个百分点，超过时在说明中给出原因，并列出跌出前 10 的题目；
- 检索耗时 p95 增加不超过 30%，超过时说明原因；
- 说明中注明改进集中在哪个词面重叠分桶。

每完成一个阶段（例如切片改造上线前），在 test 集上运行一次，并记录到 `docs/module-status.md`。记录时注明「合成基线，单来源标注」。

## 十二、后续：真实问题集

有人力或有真实提问积累后再实施，目前不做：

- **真实问题银标（无需人工标注）**：从 `chat_messages` 导出问题（差评优先，按问题去重），由 AI 去除个人信息并补全指代；用多种检索配置各取前 10 篇合并为候选池，由 AI 按 0～3 分级判定相关度并摘取证据；开发者抽查约 10%。标记为 `source=real-silver`，单独报告，此时可以计算 Recall、nDCG 和上下文精度。未复核的导出文件只放在 `.nyz-data/evaluation/`。
- **人工标注集**：业务人员盲写问题、双人标注与裁决（加权 Cohen's κ ≥ 0.6），需要 `eval_questions` / `eval_judgments` 表和管理端标注界面，人力到位后再设计。
