# nyzdata 文章样本评估

用 nyzdata 文章接口的 200 篇真实文章，评估现有 RAG 管线是否适合该数据源。评估日期 2026-10-21，共分两批，每批 100 篇。

## 样本与方法

- 来源：文章列表接口 `tagKey=9302258412`（共 7068 篇），取第 1～20 页、每页 10 条，逐篇调用详情接口，请求间隔 1.5 秒。200 篇全部成功，没有失败。
- 清洗：自行解析 `data.content`（ProseMirror/Tiptap JSON），生成结构化块、Markdown 和纯文本，并标注章节角色（content、meta、related、reference、questions）。解析器当前为 v3，未知节点为 0。
  - 没有使用接口自带的 `text` 字段，因为它把所有段落直接拼接，没有任何分隔符（200/200 篇如此）。
  - 解析出的纯文本长度约为 `text` 字段的 101%～104%，多出的只是段落分隔，内容没有丢失。
- 数据位置（已 gitignore）：`.nyz-data/nyz-articles/` 下的 `raw/`、`clean/`、`markdown/`、`index.json`，以及报告 `report.json`（合计）、`report-pages-1-10.json`、`report-pages-11-20.json`。
- 脚本：`scripts/nyz-articles/`

```sh
NYZ_ARTICLE_TOKEN=... node scripts/nyz-articles/fetch.mjs 200   # 目标总数；已保存的跳过，逐篇获取并清洗
node scripts/nyz-articles/reparse.mjs                            # 解析器升级后从 raw 重新生成
node scripts/nyz-articles/analyze.mjs [--pages=11-20]            # 合计或按列表页生成报告
```

## 现有管线测试

### 切片

现有 Worker 的做法是把空白全部折叠为空格，再按 800 字符窗口、120 字符重叠切分。下表是它和结构化切片的对比（合计 200 篇）。

| 指标 | 现有（800/120 字符窗口） | 结构化切片 |
| --- | --- | --- |
| 切片数 | 1216 | 1387 |
| 长度中位数 | 800 | 545 |
| 跨章节 | 57.1% | 0（过短章节并入下一节） |
| 从句子中间开始 | 81.3% | 均在句子或块边界 |
| 包含文章标题 | 5.3% | 100%（作为前缀） |
| 切断表格 | 48 处 | 0 |
| 混入相关阅读/本文链接 | 23.3% | 0（已排除） |
| 混入延伸思考提问 | 22.6% | 保留，但已标注角色 |
| 短于 200 字 | — | 24 |

结构化切片的规则：
- 只使用 content 和 questions 两类章节，元信息、相关阅读、本文链接不进入切片；
- 标题文字计入正文（有些章节下只有图片，标题是唯一的文字）；
- 同一章节内累积到约 800 字，不足 200 字的章节并入下一节；
- 超长段落按句切分；
- 每个切片加上「文章标题 / 章节」前缀。

### 检索与回答（代理测试）

以章节标题（只取正文章节，排除出现在 3 篇及以上文章中的模板标题）和摘要句作为问题，期望召回问题所属的文章。

| 方法 | 章节标题 Top1 / Top3（91 题） | 摘要句 Top1 / Top3（175 题） |
| --- | --- | --- |
| 现有 `/api/chat`（不重叠二元组，按文档计分） | 90.1% / 93.4% | 98.9% / 100% |
| 对照：重叠二元组 + BM25，在结构化切片上检索 | 98.9% / 98.9% | 99.4% / 100% |

- 这些问题直接取自原文，测试偏简单，只能说明词面召回本身能用，不代表对用户真实提问的效果。
- **现有回答固定取命中文档正文的前 180 字，而 95% 的文章正文以「作者：qwen3.6-plus…」或「项目名称：…」开头。** 所以就算命中了正确的文章，回答基本上也只是元信息。（第一轮评估把这一段误判为「开头引言」，已更正。）
- 现有分词会把化学式拆坏：`Na₀.₉MnO₂` 被拆成 `na`、`mno`；先做 NFKC 规范化后得到 `Na0.9MnO2`。不重叠的二元组还会丢掉一半组合，例如「固态电池中试线样品测试」中的 `样品`、`测试` 都不会成为检索词。

### 规模外推（全量 7068 篇）

| 项目 | 估算 |
| --- | --- |
| 结构化切片 | 约 4.9 万个（每篇约 6.9 个），处于 pgvector 适用范围（10 万以内）内 |
| Embedding 输入 | 约 2700 万字 |
| JSON 快照 | 约 580 MB（每篇包含正文、原始内容和切片副本），而且每次写入都要整体重写 |
| 全量同步 | 按 1.5 秒间隔约 3 小时，需要支持增量同步和断点续传 |

## 结论

**总体方向合适**：模块化单体 + 独立 Worker、PostgreSQL + pgvector、Redis + BullMQ，在这个规模下都不需要更换，也不需要独立的向量数据库。

**必须调整的部分**：

1. **元数据存储**：JSON 快照按全量估算约 580 MB，每次写入都要整体重写，不可行。应优先迁移到 PostgreSQL。
2. **采集**：现有 Worker 只支持 HTML 网页采集，文章 API 来源会直接报错，无法接入这个数据源。`scripts/nyz-articles/parse.mjs` 可以作为 Worker 解析器的原型。
3. **清洗**：`replace(/\s+/g, " ")` 会抹掉结构，导致 57% 的切片跨章节、81% 从句子中间开始。应改为基于 ProseMirror 结构生成块。
4. **章节角色**：
   - 文首元信息（作者、转载源、关键词、场景）应提取为字段，不进入正文；
   - 相关阅读和本文链接提取为关联文章和 DOI；
   - 延伸思考不做向量化，可以用作「推荐追问」；
   - 误用的标题需要降级为正文，标题文字不能丢。
5. **问答**：应改为按切片召回，再基于召回内容生成回答。现有做法下，95% 的回答只是元信息。
6. **文本规范化**：建立索引和处理查询时都应先做 NFKC 规范化；中文使用重叠二元组。

**新增需求**：

- **混合检索有必要**：语料中化学式、期刊、机构、人名（含中英对照）很多，这些精确词面只靠向量召回不稳定。关键词通道可以先在应用层生成重叠二元组，写入 `tsvector`（`simple` 配置）；`pg_trgm` 在当前数据库 locale 下对中文的效果需要先验证。Embedding 模型需要支持中英混合。
- **结构化元数据与过滤**：发布时间、分类、标签、场景（固定词表）、关键词、机构、期刊、DOI、项目负责人。像「某机构最近的钠电研究」「崔屹的项目」这类问题需要靠过滤和关键词解决，不是向量能解决的。场景可以直接作为过滤维度；关键词是长尾，更适合用于加权。
- **切片前缀**：前缀以文章标题为主（标题通常带机构和期刊），可以附加关键词。章节名大多是模板化的，单独使用几乎不提供信息。
- **文章级召回**：每篇都有摘要，可以对摘要单独向量化，先召回文章、再召回切片。
- **去重**：除内容哈希外还需要近似去重（例如 MinHash），否则同一篇论文的两版改写会占据两个召回名额。
- **增量同步**：列表开头有置顶文章，其余部分也不是严格按时间排序，不能「遇到已知文章就停」。应以 `updateTime` 判断文章是否变化，并多扫描一段重叠窗口。
- **来源与合规**：85.5% 的文章是从微信公众号转载、再经 AI 改写的。回答引用时应同时标注 nyzdata 文章和原始转载源；关于使用授权，需要和数据提供方确认。
- **PDF 附件**：报告导读和项目导读的完整内容在 PDF 里，用户问到细节时需要附件内容。优先级中等。
- **图片信息**：996 张图片只有 21% 有图注，部分文章以图片为主，这些信息暂时会丢失。后续可评估 OCR 或多模态方案，优先级低。
- **评估集**：代理测试区分度不足。建议整理 50 条以上带标注的真实问题，作为调整切片和检索时的回归基线。
