# 文章切片方案：章节父块 + 语义子块

状态：方案，未实施。实施前须先完成[真实问题评估集](evaluation-plan.md)并产出基线，切片改造以基线对比验收。

范围：只处理 nyzdata 文章接口的正文（ProseMirror 解析结果中 `role === "content"` 的块）；图片、PDF 附件不参与（见 [TODO](todo.md)「暂不实施」）。

## 一、现状与问题

现有实现（`packages/processing/src/chunking.ts`）已按章节切分、表格整块保留，但仍有以下问题：

| 问题 | 说明 |
| --- | --- |
| 章节内按字数累积 | 同一章节内累积到约 800 字就切，段落之间的关联只按长度决定 |
| 短章节章节路径错误 | 不足 200 字的章节并入下一节，切片的 `sectionPath` 记为下一节，A 节内容被标成 B 节 |
| 检索单元与上下文单元相同 | 切片小则召回精准但上下文残缺，切片大则召回稀释；当前只能取一个折中值 |
| 同章节多切片重复占用上下文 | 同一节的多个切片分别进入上下文，顺序可能打乱、内容割裂 |

## 二、样本数据（200 篇，`.nyz-data/nyz-articles/clean/`）

| 指标 | p10 | 中位 | p90 | 最大 |
| --- | --- | --- | --- | --- |
| 文章正文字数 | 1051 | 3409 | 4768 | 20763 |
| 每篇章节数 | — | 3 | 6 | — |
| 章节字数 | 98 | 605 | 2166 | 5092 |
| 内容块字数（段落/列表/表格等） | 29 | 199 | 456 | 2499 |

- 章节共 769 个：13.5% 不足 150 字，12.6% 超过 2000 字，2.7% 超过 3000 字。
- 内容块 2882 个：段落 2419、列表 201、图注 208、表格 30、引用 24；只有 2.7% 超过 600 字。
- 标题层级：87% 的内容块位于一级标题下，三级及以上标题极少。

结论：绝大多数章节本身就是完整语义单元且长度适中，适合直接作为父块；段落本身长度适中，子块按段落组合即可，很少需要拆句。

## 三、方案

### 3.1 三层结构

| 层级 | 内容 | 向量化 | 关键词词项 | 用途 |
| --- | --- | --- | --- | --- |
| L0 文章 | 标题 + 摘要 | 是（已有 `summary_embedding`） | 元数据词项（已有） | 摘要召回，不变 |
| L1 章节（父块） | 一个标题路径下的完整正文 | 否 | 否 | 回答上下文 |
| L2 子块 | 1～3 个连续内容块 | 是 | 是 | 关键词/向量召回、Rerank |

### 3.2 父块（章节）规则

1. 以解析器的标题路径（`sectionPath`）为单位，一个路径下的全部正文块组成一个父块；有子标题时，子标题自成父块，上级父块只包含子标题之前的引导段落。
2. **短章节**（不足 150 字）：保留自己的标题行（如 `### 小结`），并入上级标题的父块；没有上级标题时与相邻的同级章节合并，合并后父块的 `sectionPath` 取公共前缀，内部各小节标题保留在正文中。子块仍记录各自真实的 `sectionPath`。
3. **长章节**（超过约 2000 字）：优先按下级标题拆；没有下级标题时按内容块边界拆成若干段，每段约 1200～2000 字，记为同一章节的多个父块（`part` 序号），不在段落中间断开。
4. 没有标题的文章：整篇正文作为一个父块，超长时按第 3 条拆分。
5. 只有图片、没有正文文字的文章沿用现有兜底，用摘要作为唯一的父块和子块。

### 3.3 子块规则

1. **边界只取内容块边界**：段落、列表、引用、表格、图注各为一个内容块，子块由同一父块内 1～3 个连续内容块组成，目标约 200～500 字，上限约 600 字。
2. **表格、列表整块**：表格单独成子块；超过约 1600 字的表格按行切分并重复表头（沿用现有 `splitTable`）。列表不拆分，除非超过上限。
3. **超长段落**（超过约 600 字，约占 2.7%）：按句号、问号、分号等句末标点拆分，单句仍超长时才按长度硬切。
4. **过短内容块**（如单行图注、不足 50 字的过渡句）：与相邻内容块合并，不单独成子块。
5. **不跨父块**：子块不跨越父块边界。
6. **上下文前缀**：沿用 `文章：<标题>`、`章节：<完整标题路径>`、`关键词：<前 8 个>`，向量化输入仍为 `embeddingInput(chunk)`（前缀 + 子块正文）。

### 3.4 检索与上下文组装

```
三路召回（关键词 / 子块向量 / 摘要定位子块）→ RRF 合并子块
  → 可选 Rerank（输入为「前缀 + 子块正文」，不用父块全文，控制成本）
  → 按父块聚合：父块得分 = 最佳子块得分 + 同父块其他命中子块的少量加分
  → 按父块得分排序，依次放入上下文，直到 maxContextLength
  → 父块不超过约 2000 字时放入全文；更长时放入命中子块及其前后各一个相邻子块（按原文顺序）
```

- 同一父块只进入上下文一次，正文按原文顺序排列。
- 引用编号仍按文章分配，同一文章多个父块共用一个编号。
- `message_chunks` 继续记录命中的子块及各路得分，另记所属父块 ID，管理端问答详情显示父块。
- 知识库 `topK` 的含义从「切片数」改为「父块数」；`maxContextLength` 默认值需要随评估结果调整（父块中位约 600 字、p90 约 2200 字，5 个父块可能超过现在的 6000 字上限）。

### 3.5 存储

- 新增表 `document_sections`：`id`、`document_id`（级联删除）、`parent_id`（上级章节，可空）、`section_path`、`level`、`part`、`ord`（原文顺序）、`content`、`token_estimate`。
- `document_chunks` 新增 `section_id`（级联删除）和 `ord`（父块内顺序）。关键词词项、向量、`context` 仍只在子块上。
- 文章级的 `summary_embedding` 不变。
- 切片与父块在 `replaceDocumentChunks` 的同一事务中整体替换；`processing_version` 校验逻辑不变。
- 新增常量 `CHUNKER_VERSION` 写入文档（与 `parser_version` 并列），便于评估运行记录语料版本，并在切片规则变化时识别需要重新处理的文档。

### 3.6 影响与成本

- 子块数量：全量约 2700 万字，按子块平均约 300 字估算约 9 万个，较现在约 4.9 万个增加约 1 倍；pgvector 仍在适用范围内，HNSW 索引无需调整。
- 上线需要全量「重新处理」，并重新调用一次 Embedding（含子块与文章级向量）。
- 关键词检索的 BM25 平均长度、元数据加权按子块重新统计，需随评估集复测。
- `/api/search` 返回子块，可附带父块章节路径，前端无需大改。

## 四、暂不采用

| 方案 | 原因 |
| --- | --- |
| 基于 Embedding 相似度的语义切分 | 文章结构清晰，标题与段落已是可靠边界；额外模型调用，收益需评估集证明 |
| LLM 为每个切片生成上下文（Contextual Retrieval） | 约 9 万次 LLM 调用；先用标题路径前缀，评估后再决定 |
| 句子窗口检索（单句为子块） | 中文学术文章单句信息量不足，召回噪声大 |
| 精确 Token 计数 | 需新增分词器依赖；子块与父块按字数控制即可 |

## 五、实施步骤

1. 评估集与基线就绪（见 [evaluation-plan.md](evaluation-plan.md)），记录现有切片的基线指标。
2. `chunking.ts`：实现父块与子块生成（纯函数），单元测试覆盖短章节、长章节、无标题、表格、超长段落、纯图片文章；在 200 篇样本上输出统计（父块/子块数量与长度分布、章节路径正确性）。
3. 迁移：新增 `document_sections`、`document_chunks.section_id`/`ord`、`documents.chunker_version`；`replaceDocumentChunks` 同时写入父块。
4. 检索：`rag.ts` 增加按父块聚合与上下文组装；repository 召回结果带 `sectionId`；`message_chunks` 记录父块。
5. 在临时 schema 上全量导入样本，对比基线：Recall@10、nDCG@10、Evidence Hit@5 不下降，上下文精度提升，分题型无明显退步后再上线。
6. 业务库执行迁移并全量「重新处理」。
